# 화자 분리 개선 실험 결과 (2026-09-25)

질문: "화자 분리를 지금보다 더 개선할 방법이 있는가?" — 있다. **군집 단계만 바꾸면 같은 모델·같은 임베딩으로 화자 정확도가 83% → 93%로 오르고,
참석자 수를 모를 때의 폴백은 64%(32명으로 과분할) → 93%(7명)로 살아난다.** 임베딩 모델 교체는 이득이 없거나 작다(4절).

측정 도구는 `apps/desktop/scripts/diarBench.ts`(정답본 채점)와 실험용 Python 스크립트(재현 절차는 7절)다.
이 문서는 실측 기록이며, 제품 결정(SSOT)은 `.claude/skills/meeting-stt-dev/SKILL.md`에 반영한 뒤에만 유효하다.

### 채점 방식 (`diarBench.ts`)

정답본에 구간 끝 시각이 없으므로 **턴 i = [시작_i, 시작_i+1)** 로 본다. STT 단어(조각)마다 중앙 시각의 정답 화자를 찾고,
병합 결과의 발화 화자와 비교한다. 가중치는 글자 수(사용자가 보는 것 기준).

- **화자 정확도**: hyp 라벨 ↔ 정답 화자를 **일대일**(헝가리안)로 짝지었을 때 맞는 글자 비율. 과분할된 라벨은 짝을 못 얻어 전부 오답이 된다 (DER의 화자 혼동과 같은 관점)
- **경계 제외**: 정답 턴 경계 ±2초 안의 글자를 뺀 정확도. 정답본 해상도(1초)와 경계 어긋남을 제외한 "본문 정확도"
- **순도**: 라벨을 가장 많이 겹치는 정답 화자로 **다대일** 매핑한 비율. 과분할을 벌하지 않으므로 "군집이 섞였는지"만 본다
- **구간 시간 정확도**: STT·병합을 거치지 않은 화자 구간 자체를 시간 가중으로 채점. 화자 분리 단독 품질
- **결과 화자 수**: 흡수·병합을 거친 뒤 회의록에 남는 화자 수

정답본 시각 오프셋 −2~+2초를 시험해 0초가 최적임을 확인했다(±1초에서 0.1%p 차이). 함정 하나: 클로바는 1시간 이후 턴 헤더를 `H:MM:SS`로 적는다.
`MM:SS`만 파싱하면 60분 이후 43분이 한 턴이 되어 모든 수치가 20%p 낮게 나온다 (파서에 반영함).

## 3. 임베딩은 문제가 아니다 — 상한 분석

각 임베딩 조각(pyannote 창 × 로컬 화자, 8231개)에 정답 화자를 붙이고, **정답 중심에 가장 가까운 화자**로 분류했을 때의 정확도(길이 가중)를 재면
현재 임베딩 모델의 상한이 나온다.

| 조각 길이           | 개수 | 정답 중심 최근접 정확도 |
| ------------------- | ---- | ----------------------- |
| 0~1초               | 1227 | 44.8%                   |
| 1~2초               | 779  | 73.8%                   |
| 2~4초               | 1069 | 88.0%                   |
| 4초 이상            | 5156 | 97.1%                   |
| **전체(길이 가중)** | 8231 | **95.1%**               |

화자 중심 간 코사인 유사도는 최대 0.69(유월–이스타), 0.64(흑곰–참석자 5)이고 나머지는 0.2~0.6이라 7명은 충분히 갈라진다.
즉 **83%는 임베딩이 아니라 군집이 깎아 먹은 것**이고, 1초 미만 조각의 임베딩이 불안정하다는 점(45%)이 남은 오차의 주된 출처다.

## 4. 군집 방식 비교 (같은 분할·같은 임베딩, K=7)

sherpa-onnx 내부(분할 → 겹침 제외 → 창별 화자 조각 임베딩 → 군집 → 프레임 재라벨 → 구간화)를 Python으로 재현했다.
3분 발췌에서 CLI와 구간 경계가 0.02초 이내로 일치함을 확인했고, 전체 길이에서는 complete-linkage 동점 처리 차이로 CLI(83.4%)와 재현(74.7%)이 다르다 —
**complete-linkage는 이 정도로 불안정하다**는 뜻이기도 하다. 아래는 군집 단계만 바꾼 결과. "중심화"는 임베딩을 L2 정규화한 뒤 전체 평균을 빼는 전처리.

| 군집                               | 화자 정확도 | 경계 제외 | 순도  | 구간 시간 | 비고                                                 |
| ---------------------------------- | ----------- | --------- | ----- | --------- | ---------------------------------------------------- |
| complete (sherpa 방식)             | 74.7%       | 77.9%     | 75.0% | —         | CLI는 83.4%                                          |
| complete + 중심화                  | 86.1%       | 90.3%     | 86.2% | —         |                                                      |
| average                            | 39.1%       | 39.5%     | 39.1% | —         | 이상치 6개가 클러스터를 차지해 나머지 전부 한 덩어리 |
| average + 중심화                   | 92.8%       | 96.8%     | 92.8% | 92.3%     | K를 틀려도 안정 (아래)                               |
| ward                               | 91.5%       | 96.0%     | 93.2% | 90.2%     |                                                      |
| **k-means (n_init 10)**            | **93.2%**   | **97.1%** | 93.4% | **92.8%** | 시드 0~~3: 93.1~~93.3%                               |

효과 없거나 해로웠던 것:

- 짧은 조각(1초·2초 미만)을 군집에서 빼고 중심에 붙이기: k-means 93.2% → 89.8%(1초) / 79.2%(2초). 짧은 조각이 많아 중심 자체가 나빠진다.
- 중심화는 AHC(average·complete)에는 필수지만 k-means·ward에는 차이 없음.

### 참석자 수를 틀리게 넣었을 때

사용자가 입력하는 참석자 수는 틀릴 수 있다(이 회의도 이름 있는 참석자는 6명, 한마디 한 사람까지 세면 7명).

| 군집             | K=5   | K=6   | **K=7** | K=8       | K=9   |
| ---------------- | ----- | ----- | ------- | --------- | ----- |
| complete (현재)  | 74.7% | 74.8% | 74.7%   | 74.7%     | —     |
| k-means          | 86.3% | 93.4% | 93.2%   | **79.0%** | 76.3% |
| average + 중심화 | 85.9% | 92.7% | 92.8%   | 92.6%     | 92.6% |
| ward             | 84.7% | 91.7% | 91.5%   | 91.4%     | —     |

- K를 적게 넣으면 어느 방식이든 두 화자가 합쳐져 85~86%. 피할 수 없다.
- K를 많이 넣으면 k-means는 큰 화자를 쪼개고(79%), average + 중심화는 여분 클러스터에 이상치만 담아 92.6%를 유지한다.
  그러나 average + 중심화는 **임베딩 모델에 따라 흔들린다** (eres2netv2에서는 86.4%, 6절). k-means는 세 모델 모두 93.2~93.5%.
- **k-means + 중심 병합 보호**: 군집 뒤 중심 코사인이 0.75 이상인 클러스터 쌍을 합친다. 정답 화자 중심 간 최대 유사도가 0.69라 진짜 화자는 합쳐지지 않고,
  K를 많이 넣어 쪼개진 조각만 되돌아간다.

| k-means + 병합(0.75) | K=7   | K=8       | K=9       | K=12  | K=16  | K=20  |
| -------------------- | ----- | --------- | --------- | ----- | ----- | ----- |
| eres2net (현재)      | 93.2% | **93.4%** | **93.4%** | 93.3% | 93.1% | 93.2% |
| campplus             | 93.5% | —         | 93.3%     | —     | 93.3% | —     |

따라서 제품 기본값 후보는 **k-means(K = 참석자 수) + 중심 병합 보호(0.75)** 다. 병합 임계값은 임베딩 모델마다 다르며(eres2netv2는 80%, titanet은 86%로
0.75에서 진짜 화자까지 합쳐진다), 현재 모델(eres2net)과 campplus에서 검증한 값이다. 모델을 바꾸면 임계값도 다시 재야 한다.

## 5. 참석자 수를 모를 때 (임계값 경로)

average-linkage + 중심화의 임계값을 훑었다. 현재 앱과 같은 10초 미만 화자 흡수를 적용한 뒤의 결과.

| 임계값 (1−cos)                   | 원시 클러스터 | 흡수 후 결과 화자 | 화자 정확도 | 구간 시간 |
| -------------------------------- | ------------- | ----------------- | ----------- | --------- |
| 0.6 (중심화 없음)                | 104           | 6                 | 92.5%       | 91.6%     |
| 0.7                              | 116           | —                 | 88.4%       | —         |
| 0.8                              | 47            | 10                | 91.1%       | 90.0%     |
| **0.9**                          | **11**        | **7**             | **92.8%**   | 92.2%     |
| 현재 앱: complete 0.8 (CLI 실측) | 130           | **32**            | 63.8%       | 59.1%     |

- 임계값 0.9면 원시 클러스터 11개 중 실제 화자 7개 외의 4개는 몇 초짜리라 흡수로 사라지고, **결과 화자 수가 정답과 같은 7명**이다.
- `docs/phase1-results.md` 8절의 "임베딩 모델을 바꿔도 임계값 경로는 살아나지 않는다"는 결론은 맞지만, 원인이 complete-linkage였으므로
  **average-linkage로 바꾸면 폴백도 쓸 만해진다.** 다만 이 회의 한 편에서의 값이므로 0.9는 다른 녹음으로 재확인해야 한다.

참석자 수 경로와 같은 알고리즘으로 폴백을 통일하는 안: **k-means로 일부러 과분할(K=16)한 뒤 중심 병합 보호(0.75)** 로 되돌린다.

| 폴백                               | 원시 클러스터 | 흡수 후 결과 화자 | 화자 정확도 | 남는 여분 클러스터                            |
| ---------------------------------- | ------------- | ----------------- | ----------- | --------------------------------------------- |
| k-means K=16 + 병합 0.75, eres2net | 9             | 9                 | 93.1%       | 36초·23초·17초 (참석자 5 추정 1개 + 잡음 2개) |
| k-means K=20 + 병합 0.75, eres2net | 10            | 10                | 93.2%       |                                               |
| k-means K=16 + 병합 0.75, campplus | 9             | 7                 | 93.3%       | 28초 1개                                      |
| average + 중심화 0.9, eres2net     | 11            | 7                 | 92.8%       | 54초 1개                                      |

두 폴백 모두 정확도는 참석자 수 경로와 같고, 차이는 10~~50초짜리 여분 클러스터 1~~3개다. 현재 흡수 기준(10초)을 총 발화의 1% 같은 상대 기준으로 바꾸면 없어지지만
한마디만 한 참석자(참석자 5, 30자)도 같이 사라지므로 UI에서 "군소 화자"로 보여 주는 편이 낫다.

- k-means 결과도 92.9~93.5%로 같다. 차이는 속도뿐: **campplus가 현재 모델보다 2.5배 빠르다** (`phase1-results.md` 8절의 1.6배보다 커졌다 — 3스레드 조건).
- wespeaker CAM++ LM은 상한부터 37.8%로 이 파이프라인에서 쓸 수 없다 (Phase 1에서 wespeaker resnet34가 "전부 한 덩어리"였던 것과 같은 현상. 특징 추출 규약이 맞지 않는 것으로 보인다).
  eres2net large·common, wespeaker resnet293은 한 모델당 25~40분이 걸리는데 위 네 모델의 상한이 같아 더 볼 이유가 없어 생략했다.
- 군집을 바꾸지 않고 모델만 바꾸면(complete 열) 74.7~80.2%로, 어느 모델도 현재 CLI 기준선(83.4%)을 넘지 못한다. **모델 교체만으로는 개선이 없다**는 Phase 1의 결론이 재확인된다.

## 7. 다른 임베딩 단위

### 7-1. 문장 단위 (Whisper-first)

pyannote 창 조각 대신 **Whisper 세그먼트(3065개)** 마다 임베딩을 뽑아 군집하고, 세그먼트 전체에 그 화자를 붙였다.
겹침(2인 이상) 프레임과 비음성 프레임은 분할 결과로 걸러냈다. 임베딩 76초(eres2net).

| 군집                 | 화자 정확도 | 경계 제외 | 순도  | 구간 시간 |
| -------------------- | ----------- | --------- | ----- | --------- |
| k-means K=7          | 89.2%       | 93.1%     | 89.4% | 79.6%     |
| average + 중심화 K=7 | 91.9%       | 95.8%     | 93.3% | 82.6%     |
| complete K=7         | 86.8%       | 90.8%     | 87.0% | 77.5%     |

프레임 단위 k-means(93.2%)보다 낮다. 구간 시간 정확도가 80% 안팎으로 떨어지는 것이 원인 — Whisper 세그먼트 안에서 화자가 바뀌는 경우가 많아
(`phase1-results.md` 9절) 세그먼트 하나에 화자 하나를 붙이는 순간 경계가 무너진다. **채택하지 않는다.**

### 7-2. CLI 구간 재임베딩 (앱 통합 안 A 검증)

현재 CLI(`num-clusters=7`)가 낸 화자 구간 999개를 **라벨은 버리고** 최대 5초 조각으로 균등 분할(1582개)해 다시 임베딩하고(eres2net, 3스레드 **70초**),
TS로 옮기기 쉬운 k-means로 군집했다. 분할·CLI는 그대로 두고 앱 쪽에서 군집만 다시 하는 안이다.

| 군집 (5초 조각)                | 화자 정확도   | 경계 제외 | 순도  | 구간 시간 | 결과 화자              |
| ------------------------------ | ------------- | --------- | ----- | --------- | ---------------------- |
| k-means K=7                    | 92.3%         | 96.5%     | 93.4% | 91.8%     | 7                      |
| average + 중심화 K=7           | 92.0%         | 96.4%     | 92.9% | 92.0%     | 7                      |
| k-means K=8 + 병합 0.7         | 93.2%         | 97.2%     | 93.5% | 93.5%     | 7                      |
| **k-means K=9 + 병합 0.7**     | **93.4%**     | **97.4%** | 93.6% | **93.8%** | **7**                  |
| k-means K=12 + 병합 0.7 / 0.75 | 93.4% / 93.4% | 97.3%     | 93.5% | 93.7%     | 7 / 7                  |
| k-means K=16 + 병합 0.7        | 93.1%         | 97.2%     | 93.4% | 93.3%     | 8                      |
| k-means K=6 + 병합 0.7         | 87.0%         | 91.0%     | 87.0% | 87.7%     | 5 (진짜 화자가 합쳐짐) |
| k-means K=9 + 병합 0.75 / 0.8  | 92.1%         | 96.6%     | 93.5% | 91.6%     | 8 (여분이 안 합쳐짐)   |

- 프레임 단위 재현(93.2%)과 같은 수준이고, 과분할 + 병합(K=9~12, 0.7)에서는 **구간 시간 정확도가 93.8%로 전체 실험 중 가장 높으며 결과 화자 수도 정확히 7명**이다.
  CLI 구간은 pyannote 창 조각보다 길어(평균 4.6초) 임베딩이 안정된 덕이다.
- 병합 임계값은 조각 단위에 따라 다르다. 창 조각(4절)은 0.75, 5초 조각은 0.7~~0.75가 경계이고 K=6에서는 0.7이 진짜 화자를 합친다.
  **K를 알 때는 k-means K + 병합 0.75, 모를 때는 K=12 + 병합 0.7~~0.75**가 이 녹음에서의 안전 구간이며, 다른 녹음으로 재검증해야 한다.
- 비용: 임베딩을 두 번 하지만 두 번째는 조각이 1582개뿐이라 70초(전체 화자 분리 864초의 8%). 임베딩 시간의 대부분은 CLI가 창마다 겹쳐 뽑는 8231개 쪽이다.
- 조각 길이를 3초로 줄여도(2152개, 78초) 결과는 같다: K=7 92.0%, K=9 + 병합 0.7 **93.4%**(시간 94.0%, 7명), K=12 + 0.7/0.75 93.3%(7명). 3~5초 어느 쪽이든 된다.

## 8. 앱에 적용하려면

현재 CLI(`sherpa-onnx-offline-speaker-diarization`)는 complete-linkage만 제공하고 임베딩을 내보내지 않는다. 군집을 바꾸려면 임베딩을 앱이 직접 받아야 한다.

| 안                              | 내용                                                                                                                                                                                                                                                                            | 장단                                                                                                                                                                                        |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. CLI 구간 재임베딩 (권장)** | CLI는 지금처럼 돌리고(참석자 수 유무와 무관하게 `num-clusters`를 넉넉히), 결과 구간을 라벨 무시하고 ≤5초 조각으로 잘라 `sherpa-onnx-node`의 `SpeakerEmbeddingExtractor`로 다시 임베딩 → TS k-means(K=참석자 수, 모르면 12) + 중심 병합 보호(0.7~0.75) → 조각 라벨로 구간 재배정 | 바이너리·온보딩·모델 변화 없음. 추가 시간 70~80초(전체의 8%). 7-2절에서 **93.4% / 7명** 검증. 네이티브 애드온 1개(`sherpa-onnx-node`, `pnpm.onlyBuiltDependencies` 등록)                    |
| B. 분할·임베딩을 앱이 직접      | pyannote 분할은 `onnxruntime-node`로(창 10초·시프트 1초·powerset 7클래스 → 3화자 활성, ~100줄), 임베딩은 `sherpa-onnx-node`, 군집·재라벨은 TS                                                                                                                                   | CLI 의존 제거, 시간 그대로, campplus로 바꾸면 임베딩 2.5배 단축. 네이티브 애드온 2개, 분할 후처리(겹침 제외·창별 조각·프레임 재라벨·구간화)를 TS로 이식(Python 재현본 `diar_lab.py`가 명세) |
| C. sherpa-onnx 포크             | `FastClustering`에 k-means/병합 옵션을 추가해 CLI를 직접 빌드                                                                                                                                                                                                                   | 앱 변화 최소. 배포마다 포크 빌드·서명 유지 부담                                                                                                                                             |

어느 안이든 **기술 결정 변경**이므로 `SKILL.md` 1절 화자 분리 행과 `references/architecture.md`를 먼저 고치고 사용자 확인 뒤 구현한다.
군집 알고리즘(k-means++ · 중심 병합 · 조각 → 구간 재배정)은 순수 TS라 `packages/core`에 두고 vitest로 검증할 수 있다 (2천×512 임베딩이면 k-means는 1초 미만).
안 A의 병합 단계는 기존 `assignSpeakers`와 그대로 이어진다 — 재라벨된 구간이 `SpeakerSegment[]`로 들어가므로 `packages/core/merge.ts`는 바꿀 것이 없다.

## 10. 재현 절차

```bash
# 기준선 (현재 앱 설정, 3스레드)
```

`cluster --method=average --center --k=7`(군집·구간화, sherpa CLI와 같은 출력 형식) → `diarBench.ts`로 채점.

- **TS 구현은 Python 실험과 ±0.5%p 안에서 같다.** k-means 초기화가 달라 K=9·12의 결과 화자 수가 실험(7명)보다 1~2명 많다.
- 병합 임계값은 **0.75로 확정**한다. 0.7이 K를 크게 넣었을 때 여분 클러스터를 더 잘 되돌리지만(K=9: 8명 → 7명, +1.3%p), K를 적게 넣었을 때 실제 화자를 하나 더 합친다(K=6: 92.7% → 87.0%).
  UI에 화자 병합은 있어도 분리는 없으므로 여분 화자가 남는 쪽이 복구 가능하다.
- 참석자 수를 모를 때 남는 여분 클러스터(20~120초)는 10초 흡수로 사라지지 않는다. 임계값을 0.6까지 내려도 합쳐지지 않는 것으로 보아 잡음·겹침 구간이다. 사용자가 UI에서 합친다.
- 시간: 재임베딩 1,582조각 73.6초(3스레드), k-means 0.7~1.7초. CLI `num-clusters=12` 전체 실행은 819초로 `num-clusters=7`(864초)과 같다.
- 실제 Electron `utilityProcess`에서 빌드된 워커로 임베딩이 나오는 것을 확인했다. **Electron은 N-API 외부 버퍼를 금지**해 sherpa-onnx-node의 `readWave`·`compute`에 `enableExternalBuffer=false`를 줘야 한다 (`references/pitfalls.md`).

### geumtoro (71분 발표, 정답본 없음)

CLI `num-clusters=4` 구간(1788 / 1705 / 605 / 107초)을 재군집한 결과. 실제는 발표자 1명이 대부분을 말하고 진행자·보조 발표자·청중이 간간이 끼어든다 (`phase1-results.md`).

| K                   | 병합 | 결과 화자 발화 시간                                                |
| ------------------- | ---- | ------------------------------------------------------------------ |
| 4                   | 0.75 | 1547 / 1410 / 776 / 473                                            |
| 3                   | 0.75 | 1576 / 1440 / 1190                                                 |
| 12 (참석자 수 없음) | 0.75 | 1543 / 736 / 613 / 459 / 338 / 224 / 123 / 68 / 61 / 39 — **10명** |
| 12                  | 0.6  | 1543 / 804 / 613 / 459 / 386 / 338 / 61 — 7명                      |

정답본이 없어 정확도는 못 잰다. 참석자 수를 주면 K개로 안정되지만, **참석자 수 없이는 발표형 녹음(원거리 마이크·−44 dBFS·잡음)에서 발표자가 여러 클러스터로 남는다** —
0.6까지 내려도 7명이다. 이 녹음의 임계값 폴백은 이전(21~34명)보다 낫지만 회의 녹음처럼 좋아지지는 않는다. 참석자 수 입력을 계속 권장하고, 발표형 녹음의 폴백 개선은 후속 과제로 남긴다.
