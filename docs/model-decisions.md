서버 없이 맥에서만 도는 한국어 회의록 앱을 만들면서 어떤 모델을 왜 골랐는지 정리한 문서다.
결정마다 **무엇이 궁금했는지 → 어떻게 실험했는지 → 결과가 어땠는지 → 무엇으로 정했는지** 순서로 적었고,
마지막에 그 결정들이 모여 만들어진 최종 파이프라인 구조를 정리했다.

작성일 2026-09-25.

## 요약

- **음성 인식**은 whisper.cpp + `large-v3-turbo` 5비트 양자화(574MB). large-v3는 2.3배 느린데 품질 차이가 작았고, small은 조금 빠른 대신 오인식이 크게 늘었다.
- **화자 분리**는 sherpa-onnx + pyannote segmentation 3.0 + 3D-Speaker ERes2Net 임베딩. 가장 큰 발견은 **"몇 명인지는 모델이 아니라 사람이 알려 줘야 한다"** 는 것이다. 임계값으로 화자를 나누는 방식은 10분 녹음에서는 잘 되다가 71분 녹음에서 115명으로 쪼개졌다. 임베딩 모델을 4종 바꿔 봐도 해결되지 않았다. 그래서 녹음이 끝날 때 참석자 수를 받는다.
- **모델보다 전처리·후처리가 결과를 더 크게 바꿨다.** 음량 정규화 하나로 인식 글자 수가 36% 늘었고, 두 모델의 결과를 합치는 단위를 단어에서 문장으로 바꾸자 "문장 중간에서 화자가 바뀌는" 오류가 42%에서 1%로 줄었다.
- **로컬 LLM**은 llama.cpp + Qwen3-4B-Instruct(2.4GB). 71분 회의를 3분 40초에 요약한다. 반면 4B 모델에게 오인식 교정을 맡기면 거의 아무것도 고치지 못했다. 그래서 **코드가 발음 유사도로 후보를 만들고 모델은 O/X 판정만** 하도록 일을 나눴다.
- 외부 LLM(Claude, GPT)은 요약·용어 초안에만 선택 사항으로 둔다. 음성 인식과 화자 분리는 어떤 경우에도 로컬에서 돈다.

## 1. 후보를 좁힌 전제 조건

모델을 비교하기 전에 정해진 조건들이다. 이것만으로 후보가 크게 줄었다.

| 조건                                                      | 결과적으로 걸러진 것                                                                                                  |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| **서버 없음.** 네트워크는 첫 실행의 모델 다운로드 한 번뿐 | 상용 STT API 전부. 모델은 오프라인으로 돌릴 수 있는 공개 가중치여야 함                                                |
| **macOS 14+ / Apple Silicon 전용**                        | Windows·CUDA 고려 불필요. Metal GPU 가속을 전제로 모델 크기를 정할 수 있음                                            |
| **Electron 앱이 외부 실행 파일을 호출하는 구조**          | Python 런타임을 함께 배포해야 하는 faster-whisper, pyannote.audio 원본. 단일 바이너리인 C/C++ 구현만 남음             |
| **한국어 우선**                                           | 영어·유럽어 중심 모델(NVIDIA Parakeet, Mistral Voxtral)은 성능이 좋아도 제외                                          |
| **앱 화면보다 파이프라인 검증이 먼저**                    | 모델 크기·양자화·군집 파라미터를 스크립트로 실제 녹음에 맞춰 튜닝한 뒤 앱에 옮김. 아래 결정 대부분이 이 단계에서 나옴 |

외부 실행 파일을 호출하는 구조를 고른 이유: 추론이 죽어도 앱이 같이 죽지 않고, 플랫폼별 가속 빌드를 따로 준비하기 쉽다.
Node 네이티브 애드온으로 붙이는 방식과 브라우저(WebGPU) 안에서 추론하는 방식도 검토했지만 제품에서는 쓰지 않았다.

## 2. 실험 방법

### 2.1 환경

모든 측정은 **Apple M3 Pro (성능 코어 6 + 효율 코어 6) / 메모리 18GB / macOS** 한 대에서 했다.

### 2.2 데이터

| 이름                | 길이  | 내용                                                                                                                      | 쓰임                                  |
| ------------------- | ----- | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| 합성 회의           | 115초 | macOS TTS 한국어 음성 1개를 피치만 바꿔 3명처럼 만든 대화                                                                 | 처리 시간, 파이프라인이 끝까지 도는지 |
| 기술 발표 + Q&A     | 71분  | 아이폰 음성 메모. 발표자 1, 진행자 1, 보조 발표자 1, 청중. **청중석 녹음이라 매우 작음(−44 dBFS)**, 박수·겹쳐 말하기 있음 | 핵심 실험 대부분                      |
| 위 녹음의 10분 발췌 | 10분  | 10:00–20:00 구간                                                                                                          | 파라미터를 빠르게 반복할 때           |
| 다자간 회의         | 26분  | 앱으로 직접 녹음한 5~7명 토론                                                                                             | 화자 분리 재현 확인                   |
| 4인 회의            | 64분  | 앱으로 녹음한 실제 팀 회의                                                                                                | 결과 병합 방식 검증                   |
| 2인 회의            | 38분  | 앱으로 녹음한 대화                                                                                                        | 병합 방식의 한계 확인                 |

합성 회의는 발음이 또렷하고 잡음이 없어서 **정확도 판단에는 쓰지 않았다.** 처리 시간과 파이프라인 동작만 확인했다.

### 2.3 평가 방식

정답 전사본이나 정답 화자 라벨을 만들 여력이 없었기 때문에, 결정마다 확인 가능한 지표를 따로 정했다.

- **음성 인식**: 인식된 글자 수(놓친 구간이 있는지), 특정 구간을 사람이 듣고 비교한 오인식 사례, 처리 시간.
- **화자 분리**: 발표 녹음의 정답 발화 시간(발표자 ≈400초 / 진행자 ≈107초 / 보조 ≈22초, 10분 기준)과 비교. 생긴 클러스터 수, 10초 이상 말한 화자 수, 녹음이 진행되면서 새 화자가 계속 생기는지.
- **결과 병합**: "발화 경계에서 앞 발화가 문장부호로 끝나지 않는 비율"(= 문장 중간에서 화자가 끊긴 비율)을 대리 지표로 씀.
- **교정·요약**: 제안마다 사람이 문맥을 읽고 맞음/틀림을 판정.
- whisper.cpp 출력은 결정적이다(같은 조건 두 번 → 결과 바이트 단위로 동일). 그래서 조건별 1회 측정으로 충분하다고 봤다.

## 3. 음성 인식

### 3.1 엔진: whisper.cpp

**질문**: 같은 Whisper 가중치를 어떤 런타임으로 돌릴 것인가.

| 런타임          | 특징                                                 | 판단                                   |
| --------------- | ---------------------------------------------------- | -------------------------------------- |
| whisper.cpp     | 순수 C/C++, 의존성 없음, 바이너리 약 5MB, Metal 지원 | **채택**                               |
| faster-whisper  | Python + CTranslate2, NVIDIA GPU에 최적화            | Python 런타임 동봉 필요, Mac 가속 약함 |
| transformers.js | 브라우저 WebGPU                                      | large급 모델에서 메모리·속도 불리      |

같은 가중치라 정확도는 같다. 앱에 넣는 조건에서는 whisper.cpp가 모든 면에서 유리했다.
배포용 바이너리는 특정 버전(v1.8.4)을 소스에서 정적 빌드해 고정한다. Homebrew 설치본은 시스템 라이브러리 경로를 참조해 다른 컴퓨터에서 실행되지 않기 때문이다.

### 3.2 Whisper 외 모델을 쓰지 않은 이유

| 후보                    | 버린 이유                                                           |
| ----------------------- | ------------------------------------------------------------------- |
| NVIDIA Parakeet v3      | 영어 정확도는 turbo보다 낫지만 지원 언어가 유럽권 25개, 한국어 없음 |
| SenseVoice Small        | 한중일 특화 경량 모델이라 경량 대안으로 가치는 있음. 보류           |
| Qwen3-ASR               | 한국어·타임스탬프 지원하나 LLM 기반이라 무겁고 앱에 넣기 어려움     |
| Mistral Voxtral         | 유럽 언어 최적화, 리소스 요구 큼                                    |
| 한국어 파인튜닝 Whisper | 직접 파인튜닝은 범위 밖                                             |

### 3.3 모델 크기: `large-v3-turbo` q5_0

**가설**: tiny·base는 한국어에 부족하고 medium이 실용 하한선이다. large-v3가 한국어 최고 품질이고, large-v3-turbo는 디코더를 줄인 경량판이라 품질 손실이 작고 빠르다. 5비트 양자화로 크기를 절반 이하로 줄여도 품질 하락은 작을 것이다.

**실험 1 — 합성 회의 115초** (처리 시간만 참고)

| 모델                  | 크기   | 인식 시간 | 실시간 대비 |
| --------------------- | ------ | --------- | ----------- |
| `large-v3-turbo-q5_0` | 574MB  | 11.2초    | 0.19        |
| `large-v3-q5_0`       | 1031MB | 23.3초    | 0.20        |
| `small-q5_1`          | 181MB  | 9.2초     | 0.18        |

small은 turbo보다 2초 빠를 뿐인데 쉬운 TTS 음성에서도 오인식이 눈에 띄었다 ("안건은"→"안 꺼는", "이슈"→"이수").

**실험 2 — 실제 발표 10분 발췌** (음량 정규화 후, VAD 켬)

| 모델                  | 인식 시간\* | 글자 수 | 관찰                                                           |
| --------------------- | ----------- | ------- | -------------------------------------------------------------- |
| `large-v3-turbo-q5_0` | 53초        | 3,505   | 기술 용어 일부 오인식 ("탑올 디프" = tarball diff)             |
| `large-v3-q5_0`       | 121초       | 3,539   | 조금 더 정확 ("증분 분석", "피어디펜던시"). **2.3배 느림**     |
| `small-q5_1`          | 47초        | 3,743   | 구두점을 더 찍어 글자 수만 많음. 오인식 뚜렷 ("퓨언트팬던 씨") |

\* 화자 분리 실험과 동시에 돌려 단독 실행(약 35초)보다 느리게 나왔다. 모델 간 상대 비교로만 본다.

**결론**: **turbo-q5를 기본**으로 한다. large-v3는 "2배 이상 느립니다"라는 설명과 함께 고품질 선택지로만 두고, small은 메모리 8GB 미만 또는 코어 4개 이하 기기에서만 권장한다.

**나중에 드러난 turbo의 약점**: 64분 회의를 turbo로 돌리면 34분 이후 같은 문장을 수백 번 반복하는 **반복 환각**과 문장부호 소실이 생겼다. large-v3에서는 없었다. 기본 모델을 바꾸는 대신 초기 프롬프트 방식(3.6절)으로 반복 환각이 대부분 사라진다는 것을 확인했다.

### 3.4 음량 정규화: 모델 비교를 뒤집을 뻔한 변수

**관찰**: 71분 발표 녹음을 그대로 넣었더니, 발표자가 계속 말하는 48초 구간에서 Whisper가 11초짜리 "네네", 11초짜리 "컨셋이고요"만 냈다. 모델이 약한 것이 아니라 **소리가 너무 작아 구간을 통째로 놓친 것**이었다.

**실험 — 10분 발췌, 입력만 바꿔 비교**

| 입력                     | 평균 음량 | 글자 수   | 놓친 구간         |
| ------------------------ | --------- | --------- | ----------------- |
| 원본                     | −43.7 dB  | 2,563     | 놓침              |
| ffmpeg `loudnorm`        | −18.2 dB  | **3,505** | 복구              |
| ffmpeg `dynaudnorm`      | −27.8 dB  | 3,284     | 복구, 오인식 많음 |
| **직접 구현한 RMS 게인** | −22.6 dB  | **3,494** | loudnorm과 동등   |

**결론**: 글자 수가 36% 늘었다. 이 수준의 차이는 모델 크기를 바꿔서 얻는 차이보다 훨씬 크다.
앱에 ffmpeg를 넣지 않으려고 RMS 게인을 직접 구현했다 (50ms 프레임 음량의 상위 10% 값을 −20 dBFS에 맞추고, 증폭은 최대 +30 dB).
화자 분리 결과에는 영향이 없었다.

### 3.5 VAD(음성 구간 감지): 항상 켬 / DTW 단어 타임스탬프: 끔

**VAD**: Whisper는 무음 구간에서 없는 말을 지어낸다. 그래서 VAD로 무음을 잘라내고 인식하는 것이 기본 전략이었다. whisper.cpp에 내장된 Silero VAD(0.9MB)를 써서 별도 프로그램 없이 처리한다.

실험에서 **두 번째 이유**가 나왔다. VAD를 끄면 whisper가 단어 시각을 구간 시작 쪽에 몰아 놓아서, 화자가 바뀌는 지점의 단어가 앞사람에게 붙었다. VAD를 켜면 시각이 실제 발화 기준으로 맞춰져 경계가 정확해졌다. **VAD는 타임스탬프 정확도에도 필요하다.**

**DTW**: 단어 시각을 더 정확하게 잡는 옵션인데, 다른 가속 옵션을 꺼야 켜지고 1초 느려지면서 눈에 띄는 이득이 없었다. 끈다. 단어 시각의 부정확함은 병합 단계(5절)에서 흡수했다.

### 3.6 초기 프롬프트에 용어 넣기

**질문**: 회의 용어(GitHub, tarball, 모노레포 등)를 Whisper에 미리 알려 주면 인식 단계에서 고쳐지는가.

**실험**: 71분 녹음, turbo로 고정하고 프롬프트 조건만 바꿨다. 프롬프트는 발표 주제 용어 17개를 쉼표로 이은 문자열.

| 조건                              | 인식 시간 | 반복 환각     | 용어 교정               |
| --------------------------------- | --------- | ------------- | ----------------------- |
| 프롬프트 없음                     | 269초     | 11곳, 1,103초 | —                       |
| `--prompt`                        | 294초     | 10곳, 975초   | 첫 40초의 2곳만         |
| `--prompt --carry-initial-prompt` | 220초     | **5곳, 18초** | **오인식 39곳 중 18곳** |

- `--prompt`만 주면 첫 30초 창에서만 효과가 있다. 이후에는 직전 출력이 문맥을 밀어낸다. `--carry-initial-prompt`를 함께 줘야 매 창에 붙는다.
- **고쳐지는 것**: Whisper가 이미 아는 말(GitHub 11곳 전부, pnpm, Yarn)과 소리를 거의 맞게 들은 말(모노래퍼→모노레포).
- **안 고쳐지는 것**: 다른 음절로 들은 말(카볼→tarball, 대포→배포, 시버→semver). 이것은 교정 단계(6.3절)가 맡는다.
- **부수 효과**: 반복 환각이 1,103초에서 18초로 줄었다. 매 창 앞에 고정 문맥이 붙어 직전 출력이 스스로를 강화하는 고리가 끊긴다.
- 프롬프트 문자열이 본문에 그대로 찍히는 부작용은 없었다.

**결론**: 채택. 단 용어를 인식 **전에** 받아야 하므로 녹음 정지 화면(참석자 수를 받는 자리)에서 회의별 용어를 받는다.

## 4. 화자 분리

### 4.1 엔진: sherpa-onnx (CPU)

pyannote.audio 원본은 PyTorch 런타임만 약 1.5GB라 데스크탑 앱에 넣을 수 없다. sherpa-onnx가 pyannote 모델을 ONNX로 변환해 배포하고 있어 단일 실행 파일 + 6.6MB 모델로 돌릴 수 있다. 실제 로컬 회의록 앱(OpenWhispr)이 쓰는 구조이기도 하다.

**CoreML(Apple 가속)을 쓰지 않은 이유**: 10분 입력에서 CPU는 141초에 끝났는데 CoreML은 4분이 지나도 18%였다.
원인을 추적해 보니 임베딩 모델의 입력 길이가 발화 조각마다 달라서, 새 길이가 들어올 때마다 CoreML의 첫 호출 비용(800~900ms)이 반복됐다.
입력 길이가 고정이면 CoreML이 빠르지만(86ms vs 149ms) 가변이면 뒤집힌다(315ms vs 137ms). 길이를 패딩으로 맞추면 임베딩 값이 바뀌어서 채택하지 않았다.

### 4.2 분할 모델: pyannote segmentation 3.0

사실상 표준이고 sherpa-onnx가 지원하는 유일한 분할 모델이라 비교 없이 정했다. 처리 시간도 1초 남짓이다.

### 4.3 군집 방식: 임계값에서 참석자 수로 — 가장 크게 뒤집힌 결정

화자 분리는 "짧은 조각마다 목소리 특징(임베딩)을 뽑고 → 비슷한 것끼리 묶는" 구조다. 묶는 기준은 두 가지 중 하나를 준다.
**임계값**(이 거리 이내면 같은 사람) 또는 **클러스터 수**(정확히 k명으로 나눠라).
참석자 수를 몰라도 되는 임계값 방식이 사용자에게 편하므로 처음에는 이쪽으로 가려 했다.

**1단계 — 합성 회의**: 임계값 0.6부터 실제 화자 수 3명으로 수렴했다. 0.6을 잠정값으로.

**2단계 — 실제 10분 발췌**

| 임계값  | 감지 화자 | 주요 화자 발화 시간 |
| ------- | --------- | ------------------- |
| 0.6     | 23        | 223s / 146s / 84s   |
| 0.7     | 18        | 368s / 99s / 32s    |
| **0.8** | **12**    | 399s / 107s / 21s   |
| 0.9     | 11        | 399s / 105s / 23s   |

0.8부터 정답(400 / 107 / 22초)과 일치했다. 남은 1~8초짜리 파편 화자는 "총 10초 미만 말한 화자는 가장 가까운 주요 화자에 합친다"는 후처리로 흡수해 **12명 → 3명**. 여기서 "0.8 + 10초 흡수"로 확정했다.

**3단계 — 같은 녹음 71분 전체**

| 설정          | 클러스터 | 10초 이상 화자 | 상위 화자 발화 시간                |
| ------------- | -------- | -------------- | ---------------------------------- |
| 임계값 0.9    | **115**  | **38**         | 806s / 602s / 362s / 354s / 325s … |
| 참석자 수 4명 | 4        | 4              | 1788s / 1705s / 605s / 107s        |

실제 화자는 3명(+청중)인데 발표자 한 명이 800·600·360·350초짜리 클러스터 여럿으로 갈라졌다. 10분마다 새 화자가 5~36명씩 생겼다.

**원인**: sherpa-onnx의 군집은 complete-linkage(클러스터 안 가장 먼 두 점의 거리로 판단) + 고정 임계값이다. 이 방식은 클러스터의 "지름"을 제한하므로, 한 사람의 목소리 특징이 시간이 지나며 조금씩 퍼지면(마이크 거리, 짧은 조각, 겹쳐 말하기) 여러 클러스터로 쪼개진다. **클러스터 수가 참석자 수가 아니라 녹음 길이·발화 교대 횟수에 비례한다.** 10분에서의 성공은 짧아서 가능했던 것이다.

**4단계 — 앱에서 직접 녹음한 26분 토론**: 임계값 0.8에서 129개 클러스터, 흡수 후에도 23명. 브라우저 오디오 처리(에코 제거 등) 때문인지 의심했지만, 그런 처리가 없는 아이폰 녹음도 115개였으므로 원인이 아니다.

**결론**: 녹음을 멈출 때 **참석자 수를 입력받아 k개로 나누는 것을 기본**으로 한다.

- 참석자 수를 알면 10초 흡수를 하지 않는다. k개로 나눈 클러스터는 모두 실제 사람으로 보고, 한 마디만 한 참석자를 지우지 않기 위해서다.
- 참석자 수를 모를 때만 임계값 0.8 + 10초 흡수로 대신하고, 긴 녹음에서 화자가 과하게 나뉠 수 있다고 화면에 안내한다.
- 실제보다 크게 입력해도 k명 이하로만 나뉘므로 막지 않는다.

### 4.4 임베딩 모델: 3D-Speaker ERes2Net base 유지

**질문**: 임계값 방식이 긴 녹음에서 무너진 게 임베딩 모델이 약해서인가? 더 안정적인 모델이면 임계값 방식이 살아나는가?

**실험**: sherpa-onnx가 배포하는 화자 임베딩 모델 중 학습 데이터가 크거나 다국어인 4종을 골라 같은 조건으로 돌렸다.

10분 발췌 (정답: 400 / 107 / 22초)

| 임베딩 모델          | 크기 | 소요     | 임계값 0.9: 클러스터 / 10초 이상 / 상위 발화 |
| -------------------- | ---- | -------- | -------------------------------------------- |
| ERes2Net base (기존) | 37MB | 59초     | 9 / 3 / 418·119·14                           |
| CAM++ zh_en advanced | 26MB | **36초** | 7 / 4 / 419·108·23·14                        |
| ERes2Net v2          | 68MB | 131초    | 8 / 2 / 445·108                              |
| NeMo TitaNet large   | 96MB | 68초     | 8 / 3 / 407·121·29                           |
| WeSpeaker ResNet34   | 25MB | 70초     | 1 (전부 한 명으로 뭉침)                      |

71분 전체 (정답 3명 + 청중)

| 임베딩 모델          | 소요  | 클러스터 | 10초 이상 |
| -------------------- | ----- | -------- | --------- |
| ERes2Net base (기존) | —     | 115      | 38        |
| CAM++ zh_en advanced | 269초 | 79       | 26        |
| ERes2Net v2          | 872초 | 64       | 21        |
| NeMo TitaNet large   | 460초 | 90       | 21        |

**결과**:

- 10분에서는 어느 모델도 무너지지 않는다. 문제는 길이에서 나온다.
- 71분에서는 모든 모델이 64–115개 클러스터, 흡수 후에도 21–38명이 남는다. Q&A 구간에서 새 화자가 폭증하는 패턴도 모두 같다. **군집 방식의 한계이지 임베딩 품질의 문제가 아니다.**
- WeSpeaker는 유사도 분포가 달라 이 임계값대에서 전부 한 사람으로 뭉친다.

**결론**: 기존 모델을 유지한다. 참석자 수 방식에서는 어느 모델이든 충분하고, 바꾸면 다운로드·검증 체계를 함께 바꿔야 하는데 그만한 이득이 없다.
다만 **CAM++가 정확도 동등 이상에 1.6배 빠르고 더 작다**는 점은 화자 분리 속도를 개선할 때의 첫 후보로 남겨 둔다.

## 5. 두 모델 결과 합치기: 단어 단위에서 문장 단위로

Whisper는 "무슨 말을 했는지 + 단어별 시각"을, pyannote는 "몇 초부터 몇 초까지 누가 말했는지"를 준다. 둘을 시각으로 맞춰 붙여야 회의록이 된다.

**문제**: 실제 사용 중 "한 문장이 두 화자로 나뉘어 들어간다"는 오류가 자주 보였다 (`…악보가 그려지거든요. 무슨` / `느낌인지 알 것 같아요?`).

**원인**: 단어마다 따로 화자를 정하고 있었다. whisper.cpp의 단어 시각은 구간 끝으로 뭉개지는 경우가 많고(turbo에서 길이 0인 단어가 26%), pyannote는 1초 미만 구간을 많이 만든다(64분에 893개 중 307개). 경계 근처 단어가 옆 화자에 걸린 것이다. **모델 문제가 아니라 두 결과를 붙이는 단위의 문제였다.**

**대응**: 단어별로 배정한 뒤, 문장 안에서 다수결로 화자를 하나로 통일한다. 문장의 끝은 `.?!`, 1초 이상 쉼, 또는 8초를 넘긴 뒤의 Whisper 구간 경계.

**결과** (참석자 수 입력 방식, 지표는 문장 중간에서 끊긴 발화 경계 비율)

| 녹음                       | 이전    | 문장 다수결 |
| -------------------------- | ------- | ----------- |
| 64분 4인 회의 (large-v3)   | **42%** | **1%**      |
| 같은 회의 (turbo), 앞 34분 | 55%     | 17%         |
| 71분 발표 (turbo)          | 65%     | 23%         |

- turbo에서 수치가 덜 좋은 것은 반복 환각·문장부호 소실 때문이다(3.3절). 병합이 아니라 인식 쪽 문제다.
- 8초 상한을 둔 이유: 문장부호가 빠진 전사에서는 상한이 없으면 "문장"이 수십~수백 초로 커져 다른 사람의 말을 삼킨다.
- 버린 안: Whisper 구간 단위 배정(55% → 38%, 문장 단위보다 못함).
- **이 방법으로 못 고치는 것**: 화자 분리 자체가 실패한 경우. 38분 2인 회의는 2명으로 지정해도 한 사람이 1438초 중 68초만 배정됐다. 두 사람이 한 클러스터로 뭉친 것이라 병합 단계에서는 살릴 수 없다.

## 6. 로컬 LLM: 요약, 교정, 용어 초안

### 6.1 엔진: llama.cpp 실행 파일

음성 인식·화자 분리와 같은 방식(외부 실행 파일 호출)으로 붙였다. llama.cpp에는 HTTP 서버 모드도 있지만, 버튼을 눌렀을 때 한 번 요약하는 용도에 상주 서버·포트·좀비 프로세스 관리가 필요 없고, "네트워크를 쓰지 않는다"는 원칙을 코드로 지키기도 쉽다.
회의록 한 구간이 9천 자라 명령줄 인자 길이 제한에 걸리므로 입력·출력은 전부 파일로 주고받는다.

### 6.2 요약 모델: Qwen3-4B-Instruct-2507 (Q4_K_M, 2.4GB)

**선택 기준**

- Apache-2.0 라이선스.
- 추론 과정(`<think>`)을 출력하지 않는 비사고형 instruct 모델이라 답만 나온다.
- 4비트 양자화 2.4GB. 컨텍스트 8192토큰에서 KV 캐시가 약 1.2GB라 메모리가 적은 기기에서도 뜬다.

**실험**: 71분 회의록(40,089자, 약 28,000토큰)을 한 번에 넣을 수 없으므로 발화 경계에서 약 9천 자씩 5구간으로 나눠 각각 요약한 뒤 합쳤다(map-reduce).

| 단계         | 시간      |
| ------------ | --------- |
| 구간 요약 ×5 | 189초     |
| 합치기       | 29초      |
| **합계**     | **218초** |

회의 길이의 1/20 수준이고, 품질은 10분 발췌를 한 번에 요약한 것과 비슷했다. 측정 중 발견한 결함(출력 상한 900토큰에서 요약이 잘림, 익명 화자 라벨을 담당자로 나열, 회의록에 없는 날짜를 지어냄)은 출력 상한을 1200으로 늘리고 시스템 프롬프트에 금지 규칙을 넣어 고쳤다.

다른 모델과의 체계적인 비교는 하지 않았다. 메모리 8GB 미만 기기용 Qwen3-1.7B는 후속 과제로 남겼다.

**요약 모델은 필수가 아니다.** 첫 실행에는 필수 모델(약 620MB)만 받고 요약 모델은 설정에서 따로 받는다. "처음 요약을 누를 때 받기"는 몇 분의 다운로드와 몇 분의 추론이 이어져 사용자가 무엇을 기다리는지 알 수 없어 택하지 않았다.

### 6.3 교정: 모델에게 고치게 하지 말고 판정만 시킨다

**배경**: 요약에 "증본 문서"(changeset), "타볼"(tarball) 같은 오인식이 그대로 실렸다. 요약 모델이 원문을 충실히 옮긴 것이다. 요약할 때 오인식도 고치라고 지시하면 "회의록에 없는 내용을 만들지 마라"는 규칙과 충돌하고, 이름·숫자까지 고치려 든다. 그래서 요약과 교정을 분리하고, 교정은 **사용자가 준 용어 사전**을 근거로 하기로 했다. ("카볼"이 tarball이라는 정보는 텍스트 안에 없으므로 용어 사전 없이는 고칠 근거가 없다.)

**실험**: 같은 Qwen3-4B로 7가지 접근을 비교했다. 입력 A는 10분 회의록, B는 71분 회의록, 용어 사전 17개.

| #   | 접근                                          | 입력 | 시간  | 제안 | 맞음 | 틀림 |
| --- | --------------------------------------------- | ---- | ----- | ---- | ---- | ---- |
| 1   | 발화를 통째로 다시 쓰게 함, 용어 사전 없음    | A    | 91초  | 29   | 0    | 29   |
| 2   | 발화를 통째로 다시 쓰게 함, 용어 사전 있음    | A    | 60초  | 7    | 0    | 7    |
| 3   | 모델이 "틀린 부분 → 용어" 쌍을 짚게 함        | A    | 28초  | 4    | 3    | 1    |
| 4   | 3 + 출력 문법 고정 + 발음 검사(읽기도 모델이) | A    | 29초  | 3    | 2    | 1    |
| 5   | **코드가 발음 유사도로 후보 → 모델은 O/X만**  | A    | 9초   | 14   | 11   | 3    |
| 6   | 5와 같음                                      | B    | 38초  | 46   | 24   | 22   |
| 7   | 판정 없이 코드 후보 전부 (기준선)             | B    | 0.1초 | 118  | 24   | 94   |

**결과**:

- **4B 모델에게 문장을 고치게 하면 아무것도 고치지 못한다.** 대부분 원문을 그대로 돌려줬고, 용어를 줘도 엉뚱한 용어를 끼워 넣었다 ("대포(배포)→폴리레포").
- 모델은 "어디가 이상한지"는 꽤 짚지만 "무엇으로 바꿀지"는 자주 틀린다.
- **모델이 만든 한글 읽기는 쓸 수 없다** (semver→"세이머버전", Claude→"클라우드"). 그래서 라틴 문자 용어는 사용자가 읽기를 함께 적는다.
- **역할을 나누면 쓸 만해진다.** 코드가 자모 단위 발음 유사도(하한 0.55)로 후보를 넓게 만들고(놓치지 않기), 모델은 "이 말이 이 자리에서 뜻이 통하는가"만 O/X로 답한다(걸러내기). 정답 후보를 하나도 떨어뜨리지 않고 정밀도를 20%에서 52%로 올렸다. 출력이 후보당 몇 토큰이라 71분 회의 전체가 38초다.
- 판정 질문을 "잘못 받아 적었는가"로 하면 거의 무작위로 답했다. "뜻이 통하는가" 하나로 좁히자 안정됐다.

**결론**: 5번 방식을 채택한다. 정밀도 52%라 **자동 적용은 하지 않고** 사용자가 수락하는 제안으로만 보여 준다.

### 6.4 용어 사전 초안: 초안은 LLM, 확정은 사람

용어 사전을 빈 칸에서 시작하지 않도록, 설정의 팀 소개 문장으로 LLM이 초안을 만든다.

**실험과 결과**

| 프롬프트                                                | 결과                                                                                                         |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| "팀 회의에 자주 나올 전문 용어 40개"                    | React·Git·빌드·브랜치 같은 **일반어** 위주. 이 목록으로 교정하면 "같은→Git", "케이스→CSS" 같은 오탐이 쏟아짐 |
| "음성 인식이 틀리는 종류(영어 기술 용어·제품명·약어)만" | 용어는 구체적(Storybook, Cypress, ROAS). 한글 읽기가 자주 틀림 (npm=엘앤엠피)                                |
| + 읽기 예시, 출력 형식을 `영어 = 한글 읽기` 줄로 고정   | 일반어·문장 사라짐. 약어와 일부 단어 읽기는 여전히 틀림 (Jira=재자, Git=기트)                                |

- **팀 소개로는 그 회의의 주제 용어를 알 수 없다.** 초안은 팀 공통 용어만 채우고, 회의 주제 용어는 회의마다 따로 받는다.
- **대문자 약어 읽기는 코드가 만든다** (`CI/CD` → 씨아이 씨디). 틀릴 일이 없다.
- **단어 읽기는 4B 모델의 한계라 프롬프트로 못 고친다.** 자주 쓰는 개발·제품 용어의 읽기를 사람이 검수한 사전으로 만들어 모델의 읽기를 덮어쓴다. 사전은 읽기만 바꾸고 용어를 추가하지 않는다 (고정 목록이 되면 모든 회의를 한 분야로 끌고 간다).

## 7. 외부 LLM (선택 사항)

요약과 용어 초안은 호출 방식이 같고 프롬프트만 다르므로 하나의 공급자 추상화 뒤로 모았다. 사용자는 로컬 / Claude API / Claude Code CLI / OpenAI API 중 하나를 고른다.
이는 "네트워크는 모델 다운로드 한 번"이라는 원칙의 **명시적 예외**이므로, 외부 공급자를 고르면 회의록이 해당 회사 서버로 전송된다는 사실을 설정 화면에 적는다. **음성 인식과 화자 분리는 어떤 공급자를 골라도 로컬이다.**

| 공급자          | 모델                                                         | 이유                                                            |
| --------------- | ------------------------------------------------------------ | --------------------------------------------------------------- |
| 로컬 (기본)     | Qwen3-4B                                                     | 6.2절                                                           |
| Claude API      | `claude-opus-5` 고정, 사고 노력 `medium`                     | 요약은 정형 작업이라 높은 노력이 필요 없음                      |
| Claude Code CLI | 사용자가 CLI에 설정한 기본 모델                              | 구독 등급마다 쓸 수 있는 모델이 달라 앱이 고르면 실패할 수 있음 |
| OpenAI API      | GPT-6 Astra / Sol / Luna 중 선택 (기본 Sol), 추론 노력 `low` | 요금 차이가 커서 하나로 고정하면 비싼 쪽이나 부족한 쪽을 강요함 |

- 외부 API는 컨텍스트가 커서 71분 회의록도 한 번에 넣는다(구간 분할·합치기 없음).
- 사고·추론 토큰이 출력 상한에 포함되므로 출력 상한을 최소 16K로 둔다. 로컬용 1200을 그대로 주면 사고만 하다 잘린다.

## 8. 모델 실행 방식

모델 선택만큼 체감 속도에 영향을 준 것이 실행 방식이다.

- **가속**: whisper.cpp와 llama.cpp는 Metal GPU를 쓴다. GPU를 끄면 whisper 인식 시간이 6.1초 → 20.7초. 화자 분리만 CPU(4.1절).
- **스레드는 성능 코어 수 기준**: "전체 코어 − 2"(=10)를 주면 효율 코어까지 잡아 오히려 느려지고 발열만 는다. 화자 분리 10스레드 18.2초 → 6스레드 10.8초. whisper와 llama는 GPU가 일하므로 스레드 수에 거의 반응하지 않는다.
- **병렬 실행**: 인식과 화자 분리는 서로 독립이라 코어가 8개 이상이면 동시에 돌린다. 전체 시간 = 화자 분리 시간.
- **조용히 처리 모드**: 화자 분리 스레드를 절반으로 줄이고 순차 실행한다. 시간 +44%, CPU 부하 절반. 운영체제의 저우선순위 모드로 효율 코어에 밀어내는 방식은 10배 느려져 쓰지 않았다.

## 12. 배운 것과 남은 과제

**배운 것**

1. **짧은 샘플에서 확정하지 말 것.** 10분 발췌에서 완벽했던 임계값 0.8이 71분에서 115명이 됐다. 결정은 실제 사용 길이의 녹음으로 다시 확인해야 한다.
2. **모델을 바꾸기 전에 입력과 이음새를 볼 것.** 가장 큰 개선은 음량 정규화(+36%)와 병합 단위(42% → 1%)에서 나왔고, 둘 다 모델을 바꾸지 않았다.
3. **작은 LLM에는 생성이 아니라 판정을 맡길 것.** 4B 모델은 문장을 고치지 못했지만, 코드가 만든 후보에 O/X를 답하는 일은 빠르고 쓸 만했다.
4. **사람이 쉽게 줄 수 있는 정보는 받을 것.** 참석자 수와 회의 용어는 사용자에게 한 번 묻는 비용이 작고, 모델이 추정하는 것보다 훨씬 정확하다.

**남은 과제**

- **화자 분리 속도**: CAM++ 임베딩이 정확도 동등에 1.6배 빠르다. 속도 개선 시 첫 후보.
- **참석자 수를 모를 때**: 임베딩을 직접 받아 다른 군집 방식(평균 연결, 스펙트럴)을 돌리는 방안. 현재 CLI가 임베딩을 내보내지 않아 보류.
- **저사양 기기 요약**: Qwen3-1.7B 검토.
- **앱에 넣은 whisper 빌드의 반복 환각**: 같은 버전 소스인데 직접 빌드한 것은 71분 중 1,103초, Homebrew 빌드는 27초. 원인(라이브러리 버전·빌드 옵션) 미규명. 용어 프롬프트로 대부분 가려지지만 근본 원인은 남아 있다.
- **Whisper 토큰 확률 활용**: 실제 오인식은 확률이 낮고(카볼 0.35) 오탐 일상어는 높다(서버 0.81). 단독 기준은 못 되지만 교정 후보 가중치로 쓸 수 있다.
- **가까운 거리 2~3인 대화**: 이번 핵심 데이터는 발표 형식이라 화자 교대가 적다. 2인 회의가 한 클러스터로 뭉친 사례가 있어 재확인이 필요하다.
