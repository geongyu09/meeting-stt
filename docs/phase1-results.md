# Phase 1 파이프라인 검증 결과

측정일 2026-08-26. 측정 환경 **Apple M3 Pro / 12코어 / 18GB / macOS 25.5**.
실행 방법: `pnpm tsx scripts/pipeline.ts -- [옵션]` (pnpm에 옵션을 뺏기지 않으려면 `--` 를 먼저 준다).

## 측정 대상

| 항목             | 버전 · 경로                                                                    |
| ---------------- | ------------------------------------------------------------------------------ |
| STT              | whisper.cpp `whisper-cli` 1.8.4 (Homebrew, Metal)                              |
| 화자 분리        | sherpa-onnx `sherpa-onnx-offline-speaker-diarization` v1.13.6 (osx-arm64, CPU) |
| 화자 분할 모델   | `sherpa-onnx-pyannote-segmentation-3-0`                                        |
| 화자 임베딩 모델 | `3dspeaker_speech_eres2net_base_sv_zh-cn_3dspeaker_16k`                        |
| VAD              | `ggml-silero-v5.1.2.bin` (whisper.cpp 내장 VAD)                                |

## 픽스처의 한계 (결과 해석 전 필독)

지금 쓴 입력은 `scripts/makeFixture.ts`가 macOS `say`로 만든 **합성 회의 115초, 3화자**다.
macOS에 실제 설치된 한국어 음성이 `Yuna` 하나뿐이라, 나머지 두 화자는 같은 음성을 피치 시프트(0.84×, 1.18×)해서 만들었다.

- **전사 정확도 판단에 쓸 수 없다.** TTS는 발음이 또렷하고 잡음·겹쳐 말하기·억양 변화가 없어 실제 회의보다 훨씬 쉽다.
- **화자 분리 정확도 판단에도 쓸 수 없다.** 피치 시프트된 목소리는 임베딩 공간에서 실제 다른 사람과 다르게 놓인다.
- 아래 수치 중 **믿을 수 있는 것은 처리 시간과 배관(경로·파싱·병합)의 정상 동작**뿐이다.

**실제 녹음 측정은 아래 "실제 회의 녹음 측정" 절에 있다.** 합성 픽스처 절(처리 시간·VAD·DTW)은 배관 검증 기록으로 남긴다.

## 처리 시간 (115초 오디오, VAD 사용, DTW 미사용)

| 모델                               | 크기   | STT    | 전체(화자 분리 병렬) | RTF  |
| ---------------------------------- | ------ | ------ | -------------------- | ---- |
| `ggml-large-v3-turbo-q5_0` (기본)  | 574MB  | 11.2초 | 22.2초               | 0.19 |
| `ggml-large-v3-q5_0` (고품질 후보) | 1031MB | 23.3초 | 23.3초               | 0.20 |
| `ggml-small-q5_1` (저사양 후보)    | 181MB  | 9.2초  | 20.6초               | 0.18 |

화자 분리는 모델과 무관하게 **18~23초**로 거의 고정이며, 이 장비에서는 **화자 분리가 병목**이다
(CPU 전용 ONNX 추론, `--embedding.provider=coreml` 은 아직 시험하지 않음).

- `large-v3`는 turbo 대비 STT가 2배 느린데 합성 픽스처에서는 차이를 만들지 못했다.
- `small`은 turbo보다 겨우 2초 빠른 반면 한국어 오인식이 눈에 띄게 늘었다
  ("안건은"→"안 꺼는", "이슈"→"이수/이쉬", "재현이"→"제현이", "간헐적이라"→"간허적이라").
  **저사양 폴백 이외의 용도로 쓸 이유가 없다.**

## VAD · 단어 타임스탬프 옵션

| 조건            | 화자 경계 단어 밀림                     | 비고                                     |
| --------------- | --------------------------------------- | ---------------------------------------- |
| VAD 사용 (기본) | **없음**                                | 세그먼트 끝 기준 재매핑이 동작           |
| VAD 미사용      | 발화마다 마지막 단어가 다음 화자에 붙음 | whisper 토큰 시각이 세그먼트 시작에 몰림 |
| VAD + `-dtw`    | 없음                                    | 눈에 띄는 추가 이득 없음, STT 1초 느림   |

- **VAD는 환각 억제뿐 아니라 타임스탬프 정확도에도 이득이다.** VAD를 켜면 토큰 시각이 실제 발화 기준으로 압축돼,
  세그먼트 끝(`offsets.to`)에 맞춰 되돌렸을 때 발화 시작이 제자리를 찾는다. 끄면 whisper가 토큰 시각을
  세그먼트 시작(= 직전 세그먼트 끝)에 몰아 놓아 경계 단어가 앞 화자에게 붙는다.
- `-dtw`는 `--no-flash-attn`을 함께 줘야 켜지고(`references/pitfalls.md`), 합성 픽스처에서는 이득이 없었다.
  **기본값은 끔.** 실제 회의 WAV에서 다시 판단한다.

## `cluster-threshold` 스윕 (참석자 수를 모를 때)

| threshold | 감지 화자 수 | 화자 구간 수 |
| --------- | ------------ | ------------ |
| 0.4       | 6            | 22           |
| 0.5       | 4            | 19           |
| **0.6**   | **3**        | 18           |
| 0.7       | 3            | 18           |
| 0.8       | 3            | 18           |

값이 클수록 화자가 적게 나뉜다. 0.6부터 실제 화자 수(3)로 수렴했고 0.8까지 안정적이었다.
합성 픽스처 기준이므로 **0.6은 잠정값**이다. 참석자 수를 아는 경우에는 `--clustering.num-clusters` 를 쓰는 편이 낫다.

## 실제 회의 녹음 측정 (2026-08-26)

입력: iPhone 음성 메모로 녹음한 **한국어 기술 발표 + Q&A, 71분 0초** (`금토로.m4a`, AAC 48kHz mono 66kbps).
발표자 1명이 대부분을 말하고, 질문을 읽어 주는 진행자 1명과 보조 발표자·청중이 간간이 끼어든다.
녹음기는 청중석에 있어 **발화 RMS가 −44 dBFS**(일반 대화 −20~−25)로 매우 작고, 잡음·박수·겹쳐 말하기가 있다.

`ffmpeg -ac 1 -ar 16000 -sample_fmt s16`으로 16kHz mono WAV를 만들고(`scripts/fixtures/audio/geumtoro.wav`),
파라미터 반복에는 10:00~20:00 구간 **10분 발췌본**(`geumtoro-10min.wav`)을 썼다. 둘 다 git 제외.

### 1. 원본 그대로 돌리면 (turbo-q5, VAD, threshold 0.6)

- STT 35.0초, 화자 분리 141.3초 (RTF 0.24, 병목), 세그먼트 257개 → 발화 40개, **감지 화자 23명**.
- 병합에서 텍스트 손실은 없었다(세그먼트 글자수 = 발화 글자수 2563).
- 문제는 Whisper 자체: 화자 분리는 발표자가 계속 말한다고 잡은 124~172초 구간에서
  Whisper가 11초짜리 세그먼트 "네네", 11초짜리 "컨셋이고요", 9초짜리 "포복레이션"만 냈다. **음량이 작아 구간을 통째로 놓친 것.**

### 2. 음량 정규화 효과 (10분 발췌, turbo-q5, VAD)

| 입력                                          | 평균 음량 | 세그먼트 | 글자수   | 124~172초 구간                               |
| --------------------------------------------- | --------- | -------- | -------- | -------------------------------------------- |
| 원본                                          | −43.7 dB  | 257      | 2563     | "네네" / "컨셋이고요" / "포복레이션"         |
| ffmpeg `loudnorm` (I=−16)                     | −18.2 dB  | 228      | **3505** | "코드모드를 일부로서 실행하는 건데요 …" 복구 |
| ffmpeg `dynaudnorm`                           | −27.8 dB  | 234      | 3284     | 복구되나 오인식 더 많음                      |
| **순수 TS RMS 게인** (+24.6 dB, 클리핑 0.03%) | −22.6 dB  | 294      | **3494** | loudnorm과 동등하게 복구                     |

- 글자수 **+36%**. 놓쳤던 구간의 "포복레이션"·"패드모드"는 codemod("코드모드")였다.
- 앱에는 ffmpeg를 동봉하지 않으므로 **순수 TS RMS 게인 정규화**(`src/main/pipeline/normalize.ts`)로 확정.
  50ms 프레임 RMS의 90퍼센타일을 −20 dBFS로 맞추고, 게인 상한 +30 dB, 초과 샘플은 하드 클립.
- 정규화는 **화자 분리에는 효과가 없다** (threshold 0.8에서 원본 12명 / 정규화 16명, 주요 화자 구성은 동일).

### 3. 모델 비교 (10분 발췌, loudnorm 입력, VAD)

| 모델                  | STT 시간\* | 글자수 | 체감                                                                                         |
| --------------------- | ---------- | ------ | -------------------------------------------------------------------------------------------- |
| `large-v3-turbo-q5_0` | 53초       | 3505   | 기본. 기술 용어 일부 오인식("탑올 디프"=tarball diff, "증본분석")                            |
| `large-v3-q5_0`       | 121초      | 3539   | 조금 더 정확("증분 분석", "피어디펜던시", "AI도")하지만 **2.3배 느림**                       |
| `small-q5_1`          | 47초       | 3743   | 구두점을 더 찍어 글자수만 많고 오인식 뚜렷("퓨언트팬던 씨", "런타임 에너지", "체인지로구나") |

\* 화자 분리 스윕과 동시에 돌린 값이라 단독 실행(35초)보다 느리다.

결론: **turbo-q5 유지.** large-v3는 고품질 옵션으로만, small은 저사양 폴백으로만.

### 4. `cluster-threshold` 스윕 (10분 발췌, 원본 입력)

| 설정                          | 감지 화자 | 주요 화자 발화 시간     | 나머지                    |
| ----------------------------- | --------- | ----------------------- | ------------------------- |
| 0.6 (기존 잠정값)             | 23        | 223s / 146s / 84s       | 20명이 1~26초 파편        |
| 0.7                           | 18        | 368s / 99s / 32s / 20s  | 14명이 1~8초              |
| **0.8**                       | **12**    | 399s / 107s / 21s       | 9명이 1~8초               |
| 0.9                           | 11        | 399s / 105s / 23s       | 8명이 1~8초               |
| `num-clusters=4`              | 3         | 420s / 134s / 3s        | 4명을 요구해도 3명만 나옴 |
| 0.8 + `--min-duration-on=1.0` | 11        | 392s / 108s / 24s / 16s | 큰 차이 없음              |

- 0.8부터 주요 화자 구성(발표자 ≈400초, 진행자 ≈107초, 보조 ≈22초)이 안정되고 0.9와 거의 같다. **0.8로 확정.**
- 임계값을 올려도 **1~8초짜리 파편 화자는 없어지지 않는다.** 짧은 구간의 임베딩이 불안정한 탓이라 임계값의 문제가 아니다.
- 대응: 병합 단계 `assignSpeakers`에서 **총 발화 10초 미만 화자를 시간상 가장 가까운 주요 화자에 흡수**
  → 12명 → **3명**(발표자 / 진행자 / 보조 발표자), 발화 31개 → 15개. 10초와 20초 기준 결과가 같아 10초로 잡았다.
  참석자가 짧게 한 마디 하는 경우도 흡수되지만, Phase 3의 화자 재배정 UI로 복구하는 편이 파편 20명을 보여 주는 것보다 낫다.

### 5. CoreML 프로바이더

`--embedding.provider=coreml --segmentation.provider=coreml`은 10분 입력에서 **4분이 지나도록 18%** (CPU는 141초에 완료).
ONNX 그래프가 CoreML로 제대로 내려가지 않는 것으로 보인다. **CPU 프로바이더로 고정.**
