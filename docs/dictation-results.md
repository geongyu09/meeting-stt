# 받아쓰기(음성 입력) 측정 결과

측정일 2026-10-11. 측정 환경 **Apple M3 Pro / 12코어 / 18GB / macOS 26.5**. 앱 동봉 `whisper-cli`(v1.8.4 정적 빌드), `ggml-large-v3-turbo-q5_0.bin`, Silero VAD, 스레드 4(성능 코어 기준 `threadPlan().stt`).
`references/architecture.md` "받아쓰기" 절의 가설 값(최대 구간 길이·다듬기 규칙)은 이 문서의 수치로만 확정한다. 설계와 결정 배경은 그 절에 있다.

실행 방법:

```bash
pnpm --filter meeting-stt exec tsx scripts/dictationLatencyBench.ts            # 1절 (fixtures/output/dictation/latency.tsv)
pnpm --filter meeting-stt exec tsx scripts/dictationRefineEval.ts              # 2절 (zeroth100 turbo 출력 기준)
```

## 1. 지연 — 말이 끊긴 뒤 글자가 들어가기까지

Zeroth 낭독 문장(`scripts/research/zerothExtract.py`로 뽑은 화자별 WAV, CER 비교 셋과 겹치지 않는 시드)을 목표 길이만큼 이어 붙여 구간 WAV를 만들고,
앱과 같은 실행부(`src/main/audio/whisperOnce.ts`: Int16 변환 → RMS 정규화 → 임시 WAV → `whisper-cli` → 결과 파일)로 **spawn부터 텍스트까지의 벽시계 시간**을 쟀다.
문장 사이 0.5초, 끝에 1초 침묵을 넣어 앱이 실제로 확정하는 구간 모양과 같게 했다. 각 조건 3회, 중앙값 기준. 용어 프롬프트는 내장 읽기 사전 앞 30개를 `--prompt`로 넣고 `-mc`는 토큰 수 + 1이다.

| 목표 길이 | 실제 길이 | 용어 프롬프트 | 중앙값 | 최소 | 최대 | CER   | 비고                              |
| --------- | --------- | ------------- | ------ | ---- | ---- | ----- | --------------------------------- |
| 3초       | 3.00      | 없음          | 1.09초 | 1.08 | 1.62 | —     | 가장 짧은 문장보다 짧아 중간 잘림 |
| 3초       | 3.00      | 30개          | 1.09초 | 1.08 | 1.11 | —     |                                   |
| 8초       | 7.99      | 없음          | 1.09초 | 1.08 | 1.10 | 0.00% |                                   |
| 8초       | 7.99      | 30개          | 1.60초 | 1.60 | 1.61 | 0.00% |                                   |
| 15초      | 15.00     | 없음          | 1.60초 | 1.59 | 1.60 | 4.84% |                                   |
| 15초      | 15.00     | 30개          | 1.60초 | 1.59 | 1.61 | 4.84% |                                   |
| **20초**  | 20.15     | 없음          | 1.59초 | 1.58 | 1.60 | 5.41% |                                   |
| **20초**  | 20.15     | 30개          | 1.58초 | 1.58 | 1.60 | 5.41% |                                   |
| 30초      | 30.01     | 없음          | 1.61초 | 1.61 | 1.62 | 58.1% | 첫 문장만 나옴 (아래)             |
| 30초      | 30.01     | 30개          | 1.61초 | 1.61 | 1.63 | 58.1% |                                   |

- **구간 길이와 무관하게 1.1~1.6초다.** 시간의 대부분이 모델 로드(약 0.4초)와 30초 창 하나의 디코딩이라 3초든 20초든 같다. 값이 1.1초와 1.6초 두 묶음으로 나뉘는데 길이나 프롬프트와 일관되게 맞물리지 않아(8초 무프롬프트만 1.1초) 디코딩 경로 차이로 보고 더 파지 않았다. 어느 쪽이든 **2초 목표 안**이다.
- **용어 프롬프트는 지연을 늘리지 않는다.** 같은 길이에서 프롬프트 유무 차이가 측정 오차 안이다. CER도 같다 — Zeroth 낭독문에는 사전의 용어가 나오지 않으므로 당연하고, 프롬프트가 **해를 끼치지 않는다**는 확인이다.
- **30초 구간은 뒷부분이 잘린다.** whisper는 30초 창 단위로 돌고, 30.01초 구간은 둘째 창이 비어 첫 문장만 나왔다(58% CER). 앱은 최대 구간을 이보다 충분히 짧게 둬야 한다.
- 낭독 CER 4.8~5.4%는 `docs/stt-tuning-results.md`의 Zeroth 100문장 8.49%보다 낮다. 문장 수가 적어 흔들리는 값이고, 조건 사이 비교용이다.

**결정: `DICTATION_MAX_WINDOW_SEC = 20`** (`src/main/dictation/session.ts`). 가설 그대로다. 28초까지 지연이 같았지만, 길수록 쉬지 않고 말하는 사람의 글이 늦게 들어가고 30초 창 경계에 가까워진다. 라이브 받아쓰기(12초)보다 긴 이유는 구간 경계가 문장 중간에 걸리는 일을 줄이기 위해서다.

## 2. 다듬기 규칙 — CER을 올리지 않는가

`docs/stt-tuning-results.md`의 Zeroth 100문장 turbo 출력(`fixtures/output/zeroth100.zeroth100-turbo.txt`, 정답 `fixtures/reference/zeroth100.txt`)에 규칙을 단계별로 적용해 CER을 비교했다.
채점은 `scripts/cer.ts`(NFC → 소문자 → 글자·숫자만). 규칙은 `@meeting-stt/core/dictation`의 `refineDictationText`다.

| 조건                                       | CER       | 치환 | 삭제 | 삽입 | 바뀐 줄 |
| ------------------------------------------ | --------- | ---- | ---- | ---- | ------- |
| 규칙 없음 (whisper 출력 그대로)            | **8.49%** | 195  | 140  | 16   | —       |
| 비음성 표기 제거 + 간투사 제거 + 공백 정리 | 8.49%     | 195  | 140  | 16   | 0       |
| + 내장 읽기 사전(`TERM_READINGS`) 치환     | 8.61%     | 197  | 140  | 19   | 1       |

- **비음성·간투사·공백 규칙은 낭독문에서 아무것도 바꾸지 않았다.** 낭독문에는 간투사도 비음성 표기도 없으니 당연하고, 멀쩡한 글을 건드리지 않는다는 확인이다. 간투사가 섞인 자체 녹음 20문장 측정은 실제 받아쓰기 세션에서 모아 뒤에 더한다(아래 3절과 같은 시점).
- **내장 읽기 사전 치환은 CER을 0.12pt 올렸다.** 바뀐 줄은 하나 — `현재 전국 이슈로 부상한` → `현재 전국 Issue로 부상한`. 사전의 `Issue = 이슈` 항목이 일상 외래어를 영어 표기로 바꿨다. 정답은 한글 `이슈`다.

**결정: 받아쓰기는 내장 읽기 사전을 적용하지 않고 전역 용어 사전만 치환한다.** 내장 사전(`termReadings.ts`, 200개)은 회의록 교정에서 **오인식 후보를 찾기 위한 발음 사전**이라 `이슈`·`노션`·`슬랙`처럼 한글로 쓰는 게 자연스러운 말도 들어 있고, 받아쓰기가 그걸 영어로 바꾸면 사용자가 고르지 않은 표기 습관을 강요한다. 전역 용어 사전은 사용자가 `표기 = 읽기`를 직접 적은 것이라 치환 의도가 분명하다. `Slack`을 영어로 쓰고 싶은 사용자는 사전에 `Slack = 슬랙` 한 줄을 더하면 된다. `BUILT_IN_DICTATION_TERMS`는 이 측정(`dictationRefineEval.ts`)을 위해 코어에 남긴다.

## 3. 삽입 — `textInsert`와 앱 전체 흐름

빌드된 앱을 별도 `userData`로 띄워(playwright `_electron`) 아래를 확인했다. 사람 목소리 대신 **Zeroth 낭독 WAV 두 문장을 위젯의 청크 경로(`dictation:chunk`)로 실시간 속도(0.5초 청크)로 흘렸다** — 마이크 이후의 경로(구간 확정 → 인식 → 다듬기 → `textInsert` → 대상 앱)는 실사용과 같다.
대상 앱은 사용자 계정·작업 창이 없는 것만 썼다: **TextEdit**(메모 대용)과 **textarea 하나짜리 Electron 창**(Slack·Notion·VS Code와 같은 Chromium 기반). 다른 앱에 ⌘V를 보내면 사용자 작업 중인 창에 글이 들어가므로 Slack·Notion·Chrome·VS Code·터미널 실제 앱은 돌리지 않았다.

### 앱 전체 흐름 (TextEdit 최전면, 2026-10-11)

| 단계                                                                                                                                   | 결과                                                                                                 |
| -------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `dictation:control { toggle }`(전역 단축키와 같은 경로) → 위젯 마이크 그래프 → `listening` → 패널 받아쓰기 보기 → 다시 toggle → `idle` | 통과. 실제 마이크를 열었고 조용해서 조각은 없었다                                                    |
| 첫 문장(6.0초) + 침묵 → **1초 침묵이 찬 뒤 TextEdit에 글자가 보이기까지**                                                              | **1.23초 / 1.28초** (2회), CER 0%                                                                    |
| 둘째 문장(5.6초) 직후 `dictation:stop` → 남은 구간 인식·삽입 → 정지 완료                                                               | 0.91초 / 1.34초, TextEdit 최종 두 문장 CER **0%**                                                    |
| 클립보드 원복(텍스트)                                                                                                                  | 원복됨 (전후 `pbpaste` 동일)                                                                         |
| 녹음 중 `toggle`                                                                                                                       | 세션 없이 `errorMessage` "녹음 중에는 받아쓰기를 할 수 없습니다…"만 push, 위젯 녹음 보기 아래에 표시 |
| 받아쓰기 중 `recording:start`                                                                                                          | `assertNotDictating`이 거절, 녹음 세션 없음                                                          |
| 접근성 권한의 자식 프로세스 귀속 (개발 모드 `Electron.app`)                                                                            | 물려받음 — `textInsert`가 `AXIsProcessTrusted()` 통과(종료 0). **패키징 빌드는 미확인**              |

### 발견한 결함 — 두 번째 ⌘V부터 들어가지 않았다

첫 실행에서는 첫 문장만 들어가고 둘째 문장이 사라졌다. 도구만 세 번 연속 돌려도 첫 번째만 붙었다(종료 코드는 전부 0, 클립보드도 원복됨). 변형 넷을 만들어 가른 결과:

| 변형                                                                    | 3회 연속 삽입    |
| ----------------------------------------------------------------------- | ---------------- |
| 원안: V 키 이벤트에 `.maskCommand` 플래그만 얹어 `cghidEventTap`에 post | **첫 번째만**    |
| `cgSessionEventTap`에 post                                              | 셋 다            |
| **Command 키 자체의 keyDown/keyUp을 앞뒤에 함께 post**                  | **셋 다 (채택)** |
| 이벤트 소스를 `.hidSystemState`로                                       | 첫 번째만        |
| 클립보드 원복 생략                                                      | 첫 번째만        |

플래그만 얹은 ⌘V는 **프로세스를 새로 띄울 때마다 첫 번째만** 대상 앱에 전달된다. 실제 키 입력과 같은 순서(⌘↓ V↓ V↑ ⌘↑)로 보내도록 도구를 고쳤고, 고친 뒤 5회 연속(간격 0.1초)·앱 전체 흐름 모두 통과했다.

### `PASTE_SETTLE_MS` — 3회 연속 삽입, 옛 클립보드(`OLD-CLIPBOARD`)가 붙으면 실패

| settle           | TextEdit                     | Electron 창(textarea)        |
| ---------------- | ---------------------------- | ---------------------------- |
| 0ms              | 첫 번째가 옛 클립보드를 붙임 | 첫 번째가 옛 클립보드를 붙임 |
| 20ms             | 셋 다 정상                   | 셋 다 정상                   |
| 50 / 100 / 200ms | 셋 다 정상                   | 셋 다 정상                   |

**결정: `PASTE_SETTLE_MS = 200` 유지.** 두 대상 모두 20ms면 충분했지만, 받아쓰기는 whisper가 GPU를 막 놓은 직후에 붙여 넣으므로 느린 앱·바쁜 순간을 위해 10배 여유를 둔다. 조각 사이 지연에 0.2초가 더해져도 2초 목표 안이다.
