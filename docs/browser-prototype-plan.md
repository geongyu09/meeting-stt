## 0. 전제 — 기존 기획을 따르지 않는다

이 문서는 `.claude/skills/meeting-stt-dev/SKILL.md`의 SSOT를 **따르지 않는다**. 사용자 지시로
기존 데스크탑 앱의 방향·아키텍처·로드맵·코드 규칙을 전부 무시하고, **모델만 가져와 브라우저에서 돌아가는지
확인하는 테스트**를 만든다. 여기서 나온 결정이 `main`의 문서를 바꾸지 않으며, 반대로 `main`의 결정이
이 브랜치를 구속하지도 않는다.

- 제품이 아니다. 업데이트·서명·온보딩·설정 화면·DB 스키마는 범위 밖이다.
- **배포는 범위에 들어왔다** (2026-09-22, 사용자 지시). 다만 "정적 호스팅에 올려 브라우저에서 열리는 것"까지이고,
  서버·인증·과금·도메인 운영은 여전히 범위 밖이다. 결정과 근거는 9절.
- Electron, IPC, `src/main`, `src/preload`, better-sqlite3, 컴포넌트 레이어 규칙 모두 쓰지 않는다.
- **디자인 시스템은 데스크탑과 같다** (2026-09-24, 사용자 지시). 토큰·글꼴은 `@meeting-stt/design`을 import하고,
  공통 컴포넌트는 `references/architecture.md` "공통 컴포넌트" 계약대로 `apps/web/src/components/*`에 CSS Modules로 구현한다.
  밝은 화면만 지원한다(데스크탑과 같이 다크 보류). 그 밖의 데스크탑 규칙(레이어·세그먼트)은 여전히 따르지 않는다.
- 이 브랜치의 기존 소스 트리는 참고용으로만 둔다. 프로토타입은 `web/` 아래에 새로 만든다.

## 2. 가져오는 것

`main`에서 **파일 4개만** 복사한다. 순수 TS라 그대로 돌아간다.

| 파일                             | 하는 일                                             | 손볼 곳                                    |
| -------------------------------- | --------------------------------------------------- | ------------------------------------------ |
| `packages/core/src/merge.ts`     | 화자 구간 + 단어 타임스탬프 → 발화 단위 회의록      | 없음 (두 앱이 공용 패키지로 함께 쓴다)     |
| `src/shared/types.ts`            | `SttSegment` / `SpeakerSegment` / `MergedUtterance` | 안 쓰는 타입 제거                          |
| `src/main/pipeline/normalize.ts` | RMS 음량 정규화                                     | 파일 IO 껍데기를 `Float32Array` 입출력으로 |
| `packages/core/src/format.ts`    | 타임스탬프·회의록 텍스트 포맷                       | 없음 (두 앱이 공용 패키지로 함께 쓴다)     |

`merge.ts`의 테스트(`merge.test.ts`)도 같이 가져오면 이식이 깨졌는지 바로 안다.

**나머지는 전부 버린다.** 특히 `whisper.ts`(whisper-cli JSON 파서)와 `diarize.ts`(CLI 출력 파서)는
바이너리 출력 형식에 묶인 코드라 브라우저에서 쓸 데가 없다.

## 3. 엔진 선택

테스트니까 **Emscripten 툴체인이 필요 없는 경로**를 1순위로 잡는다. npm 설치만으로 시작할 수 있어야 한다.
결론부터 쓰면 VAD·STT·분할·임베딩 **네 모델을 전부 `@huggingface/transformers` 하나로** 돌린다.
런타임 의존성이 하나뿐이고, 모델을 전부 Hugging Face에서 받으므로 CORS 확인이 한 번으로 끝난다.

### STT: transformers.js v4 + WebGPU

- 모델: `onnx-community/whisper-large-v3-turbo_timestamped` (ONNX). 데스크탑이 쓰는 `ggml-large-v3-turbo-q5_0`과 같은 가중치의 다른 포맷.
  `_timestamped`가 붙지 않은 기본 저장소는 디코더에 cross-attention 출력이 없어 `return_timestamps: 'word'`가
  "Model outputs must contain cross attentions"로 죽는다. 파일 크기는 같다.
- WebGPU로 GPU를 쓴다. `SharedArrayBuffer`가 필요 없으므로 **COOP/COEP 헤더를 설정하지 않아도 된다** — 배포 난이도가 사라진다.
- 30초 청크 + stride는 라이브러리가 처리한다.
- **확인함**: `return_timestamps: 'word'`는 `_timestamped` 저장소에서만 동작한다. 기본 저장소로는 예외가 난다.

계획을 세울 때는 transformers.js v3을 적었지만 구현 시점의 최신은 v4(4.3.0)라 v4로 간다.

whisper.cpp WASM은 **폴백**으로만 둔다. Emscripten 빌드가 필요하고, 멀티스레드에 COOP/COEP가 붙고,
무엇보다 GPU를 못 써서 CPU로만 돈다.

### 화자 분리: transformers.js + 직접 구현한 군집

sherpa-onnx WASM은 `wasm/speaker-diarization` 예제를 직접 빌드해야 해서 테스트 단계에 맞지 않는다.
`onnxruntime-web`으로 두 ONNX를 직접 돌리는 것도 세션 관리와 전처리(임베딩 모델의 fbank)를 전부 손으로 짜야 한다.
transformers.js가 두 모델을 **이미 지원**하므로 그쪽을 쓴다. 남는 일은 군집뿐이다.

1. **분할**: `onnx-community/pyannote-segmentation-3.0`을 10초 창으로 슬라이딩. 출력은 powerset 클래스라
   argmax 후 화자별 이진 마스크로 푼다 (7클래스 = 무음 + 단독 3 + 동시발화 3).
2. **임베딩**: 창 안에서 얻은 화자 구간마다 `onnx-community/wespeaker-voxceleb-resnet34-LM`으로 임베딩 추출.
3. **군집**: 코사인 거리 + complete-linkage AHC. **참석자 수를 입력받아 클러스터 수를 고정**하는 것이 기본 경로다.

임베딩 모델을 데스크탑과 같은 3D-Speaker ERes2Net 대신 WeSpeaker로 바꾼 이유는 **배포처** 때문이다.
ERes2Net ONNX는 sherpa-onnx의 GitHub Releases에만 있어 CORS를 확인해야 하고 전처리도 직접 짜야 하지만,
WeSpeaker는 Hugging Face에 있고 transformers.js가 전처리까지 처리한다. 화자 품질이 떨어지면 그때 바꾼다.

창 사이의 화자 동일성은 **맞추지 않는다**. 창마다 나온 구간을 전부 임베딩해서 전역으로 한 번에 군집하므로
창 간 순열 정합(permutation matching)이 필요 없다. sherpa-onnx가 하는 일과 같은 구조다.

참석자 수 고정이 기본인 이유는 `docs/phase1-results.md`에 실측이 있다. 임계값 방식은 녹음이 길수록
화자가 무한히 늘어난다(10분 발췌에서 임계값 0.6이 23명, 0.8이 12명, 71분 원본은 0.9에서도 115개 클러스터).
프로토타입 UI에도 "참석자 수" 입력 칸을 반드시 둔다.

### VAD

silero v5를 STT 앞에 붙인다. 데스크탑에서 VAD를 끄면 환각뿐 아니라
**타임스탬프가 밀려서 화자 경계 단어가 앞 화자에게 붙었다**. 품질 비교의 전제 조건이다.

`@ricky0123/vad-web` 대신 `onnx-community/silero-vad`를 transformers.js의 `AutoModel`로 직접 돌린다.
vad-web은 자산 경로를 `document`에서 찾는 가정이 있어 Worker 안에서 깨지고, 어차피 의존성을 하나 더 늘린다.
동작은 whisper.cpp의 `--vad`와 같게 맞춘다 — **무음을 잘라낸 오디오로 추론하고 타임스탬프를 원래 시간으로 되돌린다.**

## 4. 처리 흐름

```
[마이크 녹음: getUserMedia → AudioWorklet(16kHz mono Float32) → Int16 블록 누적 → 정지 시 WAV Blob]
       ↓ (파일과 같은 입구로 들어간다)
[오디오 파일]
  → decodeAudioData + OfflineAudioContext → 16kHz mono Float32Array
  → RMS 정규화 (normalize.ts 이식)
  → ┌ Worker A: 화자 분리 (분할 → 임베딩 → 군집) → SpeakerSegment[] → terminate
    └ Worker B: VAD → 무음 제거 → STT → 시간 되돌리기 → SttSegment[] (단어 포함) → terminate
  → merge.ts → MergedUtterance[]
  → 화면 출력
```

Worker는 **순차로 띄우고 끝나면 즉시 terminate** 한다. WASM 메모리는 한 번 늘면 줄지 않으므로,
동시에 띄우면 최고 사용량이 두 엔진의 합이 된다. 화자 분리를 먼저 돌려서 메모리를 회수한 뒤 STT를 올린다.

녹음이 곧장 `Float32Array`로 파이프라인에 들어가지 않고 **WAV Blob을 거쳐 파일과 같은 입구로 들어가는** 이유는 세 가지다.
(1) 입력 경로가 하나뿐이라 디코딩·정규화·파형·재실행 코드를 나눠 쓸 필요가 없다.
(2) 누적을 Int16으로 하면 피크 메모리가 Float32의 절반이고, 데스크탑이 16bit PCM WAV로 쓰는 것과 결과가 같다.
(3) 녹음한 것을 그대로 내려받아 데스크탑 앱에 넣어 **같은 입력으로 두 구현을 비교**할 수 있다.

## 5. 단계

목표는 "각 단계가 혼자 돌아가는 걸 확인하고 나서 잇기"다. 중간에 막히면 거기서 멈추고 판단한다.

2026-09-18 기준 **S0~S4와 S6을 구현했고, 모델 배선은 Node(`web/scripts/smokeModels.ts`)로 확인했다.**

**2026-09-21 브라우저 첫 실측**: 개발 기기 Chrome에서 **직접 녹음한 9분 11초 회의**로 녹음 → 파이프라인 →
화자 붙은 회의록까지 관통했다. **전체 RTF 0.148로 판단선(0.5)의 3분의 1**이고, 71분 환산 약 10.5분이다.
이로써 S0·S3·S4가 통과하고 S6은 3개 기준 중 2개를 통과했다. 측정값과 해석은 6절에 있다.
남은 실측은 **S2(같은 `geumtoro-10min.wav`로 글자수 비교)와 S5(71분 완주)**, 그리고 S6의 세 번째 기준
(내려받은 WAV를 데스크탑 앱에서 열기)이다.

### S0 — 골격과 환경 확인

`web/`에 Vite + TS + React 최소 구성. `crossOriginIsolated`, WebGPU 어댑터, `deviceMemory`,
`navigator.storage.estimate()`를 찍어 보는 페이지 하나.
**완료 기준**: 개발 기기 Chrome에서 WebGPU 어댑터가 잡힌다. → 화면 첫 패널이 어댑터·shader-f16·`crossOriginIsolated`·저장소 여유를 찍는다. **통과** (2026-09-21, 어댑터 확인).

패널은 **모델 캐시 상태**(고른 모델·dtype 기준으로 몇 개가 Cache Storage에 있는지)와 **영구 저장 승격 여부**도
같이 찍는다. 실행할 때마다 나오는 "내려받는 중" 문구만으로는 캐시에서 읽는지 네트워크에서 받는지 구분이 안 되기 때문이다 (§7).

### S1 — 오디오 로드

파일 드롭 → 16kHz mono `Float32Array` → 정규화 → 파형/길이/평균 dBFS 표시.
**완료 기준**: 71분 파일을 넣어도 탭이 죽지 않고 정규화 전후 dBFS가 데스크탑 결과와 맞는다.
→ dBFS는 **일치 확인**. 10분 발췌에서 −44.6 → −20.0 dBFS(게인 +24.6dB)로 `docs/phase1-results.md`의 −44 dBFS와 맞는다.
71분 디코딩은 브라우저에서 확인 필요.

### S2 — STT 단독

transformers.js로 모델 받고 텍스트 뽑기. 모델 다운로드 진행률, 처리 진행률, 취소.
**완료 기준**: 10분 발췌에서 단어 타임스탬프가 붙은 세그먼트가 나오고, 글자수가 데스크탑(3505자) 대비 ±10% 이내.
→ 단어 타임스탬프는 `_timestamped` 저장소에서 **동작 확인**이고, 2026-09-21 브라우저 실행에서도 단어 시각 기반
병합이 정상 동작했다(9분 11초 녹음에서 발화 51개·2612자). **다만 글자수 기준은 미판정이다** — 입력이 다른
오디오라 데스크탑의 3505자와 비교할 수 없다. 같은 `geumtoro-10min.wav`(원본 음량, 앱이 입구에서 정규화하므로
`-rmsnorm` 쪽을 넣으면 이중 게인이 된다)를 넣어야 판정된다.

### S3 — 화자 분리 단독

분할 → 임베딩 → 군집. 참석자 수 입력 지원.
**완료 기준**: 10분 발췌에서 참석자 수 3으로 돌렸을 때 발표자/진행자/보조 구성이 나온다.
→ 합성 픽스처(115초, 3명)에서 **프레임 정확도 94.9%, 클러스터 3개**. 10분 실제 녹음도 클러스터 3개로 완주했다.
2026-09-21 브라우저(WebGPU)에서 9분 11초 녹음을 참석자 수 3으로 돌려 **클러스터 3개, 임베딩 158개 →
화자 구간 118개, 16.4초(RTF 0.030)** 로 **통과**. 회의록의 화자 구분도 사용자 확인을 받았다.

### S4 — 병합

`merge.ts` 붙이고 `merge.test.ts` 통과 확인.
**완료 기준**: 화자가 붙은 회의록이 화면에 나온다.
→ `merge.test.ts`가 이식본에서 그대로 통과하고, 스모크 테스트가 화자 붙은 회의록을 출력한다.
2026-09-21 브라우저에서도 화면에 화자가 붙은 회의록이 나와 **통과**. 병합 자체는 0.0초로 측정에 잡히지 않는다.

### S5 — 전체 실행과 측정

71분 원본으로 끝까지. 6절 표를 채운다.
**완료 기준**: 완주 + 측정값 기록. **아직 안 함.** 9분 11초 실측(RTF 0.148)을 외삽하면 71분에 약 10.5분으로
판단선(35.5분)에 3.4배 여유가 있으나, 71분의 관문은 속도가 아니라 **메모리**다 — Float32 273MB가 워커를
왕복하고 WASM은 인스턴스당 4GB가 상한이다. 군집은 관문이 아니다(임베딩 158개 → 71분 환산 약 1,220개,
거리 행렬 Float64 약 12MB).

### S6 — 마이크 녹음

`getUserMedia` + AudioWorklet으로 16kHz mono Float32 PCM을 직접 모은다. MediaRecorder는 쓰지 않는다 —
컨테이너(webm/opus)로 압축돼 나오면 다시 디코딩해야 하고, 손실 압축이 STT 앞에 한 겹 더 끼어든다.

- 워크릿이 보내는 청크는 **Int16 블록(10초 단위)으로 누적**한다. Float32로 들고 있으면 71분에 273MB이고,
  Int16이면 절반이면서 데스크탑이 쓰는 16bit PCM WAV와 값이 같다.
- 정지하면 블록을 이어 붙여 **WAV Blob → `File`** 로 만들고, 드롭한 파일과 **같은 입구**(`loadAudio`)로 넣는다.
- 녹음 중에는 경과 시간과 **입력 세기를 dBFS로** 보여 준다. 원거리 마이크로 한 시간을 녹음한 뒤에야
  음량이 모자랐다는 걸 알게 되는 것이 이 프로젝트가 이미 한 번 치른 대가다 (7절 첫 항목).
- 녹음본은 **WAV로 내려받을 수 있게** 둔다. 같은 파일을 데스크탑 앱에 넣어야 두 구현을 비교할 수 있다.

**완료 기준**: 개발 기기 Chrome에서 몇 분짜리 회의를 녹음해 (1) 정지 즉시 파형·dBFS가 나오고,
(2) 같은 화면에서 이어 돌린 파이프라인이 화자가 붙은 회의록을 내놓고, (3) 내려받은 WAV가
데스크탑 앱에서도 열리면 통과. → 2026-09-21에 **(1)·(2) 통과** (9분 11초 녹음, 6절 표). **(3)은 미확인.**

## 6. 측정과 판단 기준

S5에서 아래를 채운다. 비교 대상은 `docs/phase1-results.md`의 M3 Pro 네이티브 실측이다.

| 항목             | 데스크탑 (네이티브, Metal) | 브라우저 (측정)                       |
| ---------------- | -------------------------- | ------------------------------------- |
| STT              | 35초 / 10분 (RTF 0.058)    | RTF **0.118** (9분 11초, 65초)        |
| 화자 분리        | 141초 / 10분 (RTF 0.24)    | RTF **0.030** (9분 11초, 16.4초)      |
| 전체, 71분       | —                          | 미측정 (9분 실측 0.148 → 환산 10.5분) |
| 피크 메모리      | —                          | 미측정                                |
| 모델 총 다운로드 | 574MB + 32MB               | q4f16 기준 564MB + 32MB + 2MB(VAD)    |

**판단선**: 전체 RTF가 0.5를 넘으면(60분 회의에 30분 이상) 이 구성으로는 쓸 물건이 안 된다.
그때는 whisper를 small로 낮추거나, 화자 분리를 빼고 텍스트만 뽑는 쪽으로 범위를 줄인다.
→ 9분 실측 0.148로 **1차 통과**. 71분 완주(S5)로 확정한다.

### 피크 메모리를 재는 방법

71분의 관문은 속도가 아니라 메모리인데(S5) 소요 시간과 달리 메모리는 저절로 남지 않는다.
앱이 `performance.measureUserAgentSpecificMemory()`를 **실행 내내 반복 호출해 단계별 최고값**을 들고,
결과표에 피크와 그중 워커 몫을 찍는다. 이 API를 고른 이유는 **dedicated worker의 메모리까지 같은
agent cluster로 묶어** 한 번에 세고, 워커가 `terminate`되면 그만큼 즉시 빠지므로
"순차로 띄워 피크를 낮춘다"는 4절의 전제를 그대로 검증하기 때문이다.

**대가가 하나 붙는다.** 이 API는 `crossOriginIsolated`에서만 돌아가는데 이 프로토타입은 3절대로
헤더 없이 도는 것이 기본이라, S5는 **`VITE_COEP=1`로 띄워야** 메모리가 찍힌다. 그런데 격리를 켜면
`applyWasmThreads`가 WASM 스레드를 코어 수만큼 올려서 **VAD가 9분 실측과 다른 조건**이 된다.
그래도 이 조건으로 한 번만 돌린다 — VAD는 전체의 5%고 켜는 쪽이 더 빠르므로 판단선(0.5) 판정이
뒤집힐 일이 없다. 대신 S5 결과에는 `VITE_COEP=1`이었다고 반드시 같이 적는다.

한계는 분명히 둔다. 이 API는 GC 시점에 맞춰 값을 돌려주므로 **호출 하나가 수 초 걸리고**, 그 사이의 짧은
치솟음은 놓친다. 그리고 세는 대상이 JS 쪽 메모리라 **WASM 힙·WebGPU 버퍼·`AudioBuffer` 같은 외부 할당은
빠질 수 있다** — 하필 디코딩 피크와 추론 피크가 거기 있다. 그래서 측정값은 **하한선**으로 읽고,
표에 적는 최종 숫자는 실행 중 **Chrome 작업 관리자(⇧+Esc)의 탭·워커 메모리 풋프린트**와 함께 본다.
둘이 크게 벌어지면 벌어진 쪽이 외부 할당의 크기다.

### 2026-09-21 첫 브라우저 실측

입력은 **개발 기기에서 직접 녹음한 9분 11초(551초) 회의**다. 참석자 수 3, STT·화자 분리 **모두 WebGPU**,
`large-v3-turbo` + q4f16, 모델 캐시가 채워진 **두 번째 실행**이다.

| 단계            | 소요     | RTF (오디오 551초 기준) |
| --------------- | -------- | ----------------------- |
| 디코딩 + 정규화 | 0.1초    | —                       |
| VAD             | 4.1초    | 0.007                   |
| 화자 분리       | 16.4초   | 0.030                   |
| 음성 인식       | 65초     | 0.118                   |
| 병합            | 0.0초    | —                       |
| **전체**        | **81초** | **0.148**               |

부수 값: 발화 길이(VAD) 277초(전체의 50.3%), 화자 3명, 임베딩 158개 / 화자 구간 118개, 발화 51개, 2612자.

읽어낼 것 세 가지.

1. **병목이 뒤바뀌었다.** 데스크탑의 병목은 화자 분리(RTF 0.24)였는데 브라우저에서는 STT가 전체의 80%를
   쓴다. 데스크탑에 뒤지는 항목은 STT 하나뿐이다(0.058 → 0.118, 2배). 원래 이 절은 "whisper는 WebGPU로
   구제할 여지가 있지만 화자 분리는 그렇지 않을 수 있다"고 적었는데, **실측은 그 반대였다.**
2. **화자 분리 8배는 순수한 속도 이득이 아니다.** `diarizeWorker.ts`의 `WINDOW_STEP_SEC = 10`으로 창을
   겹치지 않고 밀어서 sherpa-onnx보다 추론량 자체가 적다. 대가는 창 경계 정확도이고 근거는 합성 픽스처
   프레임 정확도 94.9% 하나뿐이다. **속도 예산이 3배 남았으니 겹침(STEP 5초)을 사서 품질을 올릴 여지가
   있다** — 이 숫자의 실질적 의미는 이쪽이다.
3. **기본 설정은 아직 미측정이다.** 이 실측은 화자 분리를 WebGPU로 바꿔 돌린 값이고
   `DEFAULT_OPTIONS.diarizeDevice`는 여전히 `wasm`이다. 헤더가 없으면 `crossOriginIsolated`가 꺼져
   ORT WASM이 1스레드로 도니까(`wasmThreads.ts`) 기본값 경로는 훨씬 느릴 수 있다. 기본값을 `webgpu`로
   바꿀지는 WASM 경로를 한 번 재고 정한다.

## 7. 알려진 함정

기존 프로젝트에서 이미 대가를 치르고 확인한 것들이다.

- **음량이 작은 녹음은 Whisper가 수십 초를 통째로 놓친다.** 원거리 마이크 녹음에서 11초짜리 세그먼트가
  "네네" 한 마디로 나왔다. 정규화를 빼고 비교하면 안 된다.
- **VAD 없이 추론 금지.** 무음에서 환각을 만들고 타임스탬프가 밀린다.
- **silero v5에 512샘플만 넣으면 안 된다.** 직전 창의 끝 64샘플을 앞에 붙여 576샘플을 넣어야 한다
  (silero-vad 저장소 `OnnxWrapper`가 하는 일). 컨텍스트 없이 돌렸더니 10분 원거리 녹음에서
  발화가 **383초 대신 175초**로 잡혔다. 조용한 녹음일수록 차이가 크다.
- **Whisper ONNX 저장소는 `_timestamped`가 붙은 쪽을 써야 단어 타임스탬프가 나온다.** 기본 export에는
  cross-attention 출력이 없어 `return_timestamps: 'word'`가 예외로 죽는다.
- **임계값 군집은 긴 녹음에서 화자가 무한정 늘어난다.** 참석자 수 입력이 기본 경로다.
- **`decodeAudioData`는 컨텍스트의 샘플레이트로 푼다.** 16kHz `OfflineAudioContext`에 디코딩을 맡기면
  원본을 48kHz로 통째로 푸는 일(스테레오 1시간 1.3GB)을 피할 수 있다. 프로토타입은 이 방식을 쓴다.
- **WASM은 32비트 주소라 인스턴스당 4GB가 상한**이고 실제 한도는 더 낮다. WebGPU 버퍼는 이 상한과 별개다.
- **WASM 메모리는 줄지 않는다.** Worker를 terminate해야 회수된다.
- 모델 파일은 CORS 헤더를 주는 곳에서 받아야 한다. Hugging Face는 준다. GitHub Releases는 확인이 필요하다.
- **transformers.js는 캐시에서 읽을 때도 `download` 진행률 이벤트를 그대로 쏜다.** `hub.js`가 `cacheHit`을
  판정해 놓고도 진행률 콜백은 조건 없이 부른다. 진행률만 보고 "또 받는다"고 판단하면 안 된다. 실제 네트워크
  사용 여부는 DevTools Network 탭이나 S0 패널의 캐시 상태로 본다.
- **Cache Storage는 origin 단위라 포트가 밀리면 통째로 미스가 난다.** 5180이 점유돼 있으면 Vite가 조용히
  5181로 올라가고 받아 둔 570MB가 없는 셈이 된다. `strictPort: true`로 포트를 고정해 이 사고를 막는다.
- **저장소 기본 모드는 best-effort라 디스크가 빠듯하면 브라우저가 origin 단위로 비운다.**
  `navigator.storage.persist()`로 승격해 두지 않으면 받아 둔 모델이 소리 없이 사라진다.
- **`persist()` 승격은 배포된 origin에서 거절되는 게 정상이다.** localhost는 대체로 그냥 승인되지만,
  https 도메인은 설치·북마크·체류 이력 같은 사이트 관여도가 쌓이기 전까지 best-effort로 남는다.
  "두 번째 방문부터 네트워크를 쓰지 않는다"가 로컬에서만 성립할 수 있다는 뜻이다.
- 550MB를 `Uint8Array`로 들고 있으면 JS 힙과 WASM 힙에 두 번 올라간다. 넘긴 뒤 참조를 바로 끊는다.
- **워크릿을 destination까지 잇지 않으면 `process()`가 한 번도 불리지 않는다.** 마이크 → 워크릿만 이어 두면
  청크가 오지 않고, 그냥 이으면 마이크 소리가 스피커로 되돌아간다. `gain = 0`인 `GainNode`를 사이에 둔다.
- **`AudioContext({ sampleRate: 16000 })`이 장치에 따라 무시된다.** 실제 `context.sampleRate`를 확인하고
  다르면 녹음을 시작하지 말고 안내한다. 48kHz로 받아 놓고 16kHz라고 우기면 전사 결과가 통째로 어긋난다.
- **Vite가 4KB 미만 에셋을 `data:` URL로 인라인한다.** 워크릿이 인라인되면 CSP가 붙은 환경에서
  `audioWorklet.addModule('data:…')`이 막히고, 개발 서버에서는 재현되지 않는다. 워크릿은 인라인에서 뺀다.
- **녹음 중 탭을 닫거나 새로고침하면 녹음이 통째로 사라진다.** 디스크에 쓰지 않는 구성이라 그렇다.
  프로토타입은 `beforeunload` 경고까지만 하고, 길게 녹음할 일이 생기면 그때 OPFS를 본다.

### 커맨드를 덮는 이유

루트 `package.json`의 `postinstall`이 `electron-builder install-app-deps`다. 기본 설치 커맨드를 그대로 쓰면
웹 빌드에 쓰지도 않는 Electron 바이너리를 내려받고 better-sqlite3를 네이티브 리빌드하려 든다.
그래서 설치를 `pnpm install --frozen-lockfile --ignore-scripts`로 덮는다. vite가 쓰는 esbuild는
JS API가 플랫폼 패키지의 바이너리를 직접 찾으므로 설치 스크립트 없이도 동작한다.

### COOP/COEP를 붙인다

계획 §3에서 "WebGPU면 헤더가 필요 없다"고 적었고 그건 여전히 맞다. 하지만 `sttWorker`의 기본 장치는 `wasm`이고
`wasmThreads.ts`는 `crossOriginIsolated`가 아니면 스레드 수를 1로 둔다. WebGPU가 없는 방문자는 large-v3-turbo를
싱글 스레드 WASM으로 돌게 되는데 이건 쓸 수 있는 수준이 아니다. 그래서 프로덕션에도 개발 서버의 `VITE_COEP=1`과
같은 헤더를 붙인다.

`require-corp`가 아니라 `credentialless`를 쓰는 이유는 개발 서버와 같다 — CORP 헤더가 없는 Hugging Face 응답이 막히기 때문이다.
`credentialless`를 모르는 브라우저(Safari)는 헤더를 무시하고 격리되지 않은 채로 돌아가므로, 폴백이 지금과 같다.

### 캐시 헤더

`dist` 27MB 중 26MB가 `ort-wasm-simd-threaded.asyncify.wasm` 하나다. 파일명에 콘텐츠 해시가 붙으므로
`/assets/*`에 `immutable`을 줘서 재방문 때 다시 내려받지 않게 한다. 모델 600MB는 우리 origin을 거치지 않고
브라우저가 Hugging Face에서 직접 받으므로 호스팅 대역폭과 무관하다.

### 남는 제약

- Vercel Hobby 플랜은 상업적 사용을 허용하지 않는다. 데모를 넘어서면 플랜을 올려야 한다.
- 마이크(`getUserMedia`)는 보안 컨텍스트가 필요하다. 호스팅이 https를 주므로 추가 작업은 없다.
- 배포 origin에서는 `persist()` 승격이 거절될 수 있다 (7절).
- 브랜치(`test/browser-stt`)를 원격에 올리지 않으므로 Git 연동 자동 배포를 쓰지 않는다. 로컬에서 CLI로 올린다.

## 10. 화면 (2026-09-25 리디자인)

사용자 지시로 Design 캔버스 시안의 웹 아트보드 4장(시작·녹음 중·처리 중·회의록)에 맞춰 화면을 다시 만든다.
"예쁜 UI는 비목표"였던 1절의 항목은 이 절로 대체된다. 값·구조의 근거는 `references/architecture.md` "화면 디자인"이고,
이 절은 웹 화면이 데스크탑과 **다르게** 하는 것만 적는다.

### 라우트

`react-router` v8 `createBrowserRouter`를 쓴다. 데스크탑은 `file://` 때문에 해시 라우터지만 웹은 정적 호스팅이라
경로가 그대로 URL이 되는 쪽이 자연스럽다. Vercel은 `vercel.json`의 `rewrites`로 모든 경로를 `index.html`에 돌린다.

| 경로            | 화면                                                                                            |
| --------------- | ----------------------------------------------------------------------------------------------- |
| `/`             | 시작 — 제목, 참석자 수 스테퍼, "녹음 시작", 환경 한 줄(WebGPU·모델 캐시), "오디오 파일로 시작"  |
| `/record`       | 녹음 중 — 타이머, 파형형 레벨 미터, 참석자 수 스테퍼, "녹음 정지하고 회의록 만들기"             |
| `/meetings/:id` | 기록 하나 — 상태가 `done`이면 회의록, 아니면 처리 화면(단계 목록·전체 진행률·취소)              |
| `/test`         | 리디자인 전의 프로토타입 페이지(환경 패널·장치/모델 선택·측정표). 실측·디버깅용으로 그대로 둔다 |

사이드바(272px)는 모든 화면에 공통이다: 새 녹음 버튼(녹음 중이면 경과 시간과 "녹음 중"으로 바뀌고 `/record`로 이동,
처리 중이면 비활성), 기록 검색, 이 브라우저에 저장된 기록 목록(처리 중이면 진행률 막대), 하단 안내 한 줄.

### 저장 — IndexedDB

시안의 "이 브라우저에 저장된 기록"을 위해 기록을 IndexedDB(`meeting-stt-web` / `meetings`)에 남긴다. 서버는 없다.
한 기록은 `{ id, title, createdAt, durationSec, speakerCount, status, audio(Blob), utterances, speakerNames, processing, errorMessage }`이고
`status`는 `recorded → processing → done | error`다. 오디오 Blob을 기록과 같이 두므로 처리 중 탭을 닫아도 다시 열어 "회의록 만들기"로 이어 갈 수 있다.
검색은 제목과 발화 텍스트를 클라이언트에서 부분 일치로 거른다 (데스크탑 `meetings:search`와 같은 대상).

**시안과 다른 점 두 가지.** (1) 녹음을 "조금씩" 저장하지 않고 **정지할 때** 한 번 저장한다 — 7절의 OPFS 미결과 같은 이유로,
녹음 중 탭을 닫으면 녹음은 사라진다. 화면 문구도 그렇게 적는다. (2) 참석자 수는 **필수**다. 시안의 "비우면 자동으로 나눕니다"는
임계값 군집이 필요한데 이 프로토타입은 참석자 수 고정만 구현했고(3절), 임계값 방식은 채택하지 않는다.

### 처리 화면의 단계

`runPipeline`의 실행 순서(화자 분리 → 음성 인식 → 병합)를 그대로 보여 준다. 시안은 음성 인식을 먼저 그렸지만
실제 순서와 다르면 "대기" 단계 뒤에 "진행 중"이 오는 모양이 되어 바꾸지 않는다. 단계는 다음 네 개다.

1. 녹음 저장 — 저장이 끝난 상태로 시작한다 (길이 표시)
2. 화자 구분 — `diarize` 단계
3. 음성 인식 — `stt` 단계
4. 회의록 정리 — `merge`

시안의 "음성 인식 모델 받기 · 처음 한 번"은 **별도 단계가 아니라 각 단계의 앞부분**이다. 워커가 자기 모델을 추론 직전에 받기 때문이다
(화자 분리 워커가 분할·임베딩, STT 워커가 VAD·Whisper). 워커의 `kind: 'download'` 진행률이 오면 그 단계가 "○○ 모델 받기 · 처음 한 번"으로 바뀌고,
`kind: 'run'`이 오면 추론으로 넘어간다. "처음 한 번" 꼬리표는 실행 전 `probeModelCache`에서 빠진 파일이 있었을 때만 붙인다 —
transformers.js는 캐시에서 읽을 때도 `download` 이벤트를 쏘기 때문이다 (7절).

전체 진행률은 단계 가중치(화자 구분 30 · 음성 인식 60 · 정리 10)로 합산하고, 받기가 예상되면 각 단계 몫의 40%를 받기 구간에 준다.
계산은 `src/state/jobProgress.ts`의 순수 함수이고 vitest로 검증한다.

### 실행 옵션

리디자인 화면에는 장치·모델·정밀도 선택이 없다. 환경을 보고 자동으로 정한다 — WebGPU가 있으면 STT·화자 분리 모두 `webgpu`,
shader-f16이 있으면 `q4f16` 아니면 `q4`; WebGPU가 없으면 둘 다 `wasm` + `q4`. 모델은 `large-v3-turbo` 고정이다.
옵션을 손으로 바꿔 재야 할 때는 `/test`를 쓴다.

상단 바: 전체 복사(plain) · 마크다운으로 복사 · 텍스트 파일로 저장 · 더보기(삭제, 2단계 인라인 확인).
