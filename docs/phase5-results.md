# Phase 5-1 로컬 요약 검증 결과

측정일 2026-08-26. 측정 환경 **Apple M3 Pro / 12코어 / 18GB / macOS 25.5**.
실행 방법: `pnpm tsx scripts/summarize.ts <회의록.txt>` (`pnpm tsx scripts/setupBin.ts`로 `llama-cli`,
`pnpm tsx scripts/setupModels.ts --summary`로 요약 모델을 먼저 받는다).

## 측정 대상

| 항목      | 버전 · 경로                                                                         |
| --------- | ----------------------------------------------------------------------------------- |
| 엔진      | llama.cpp `llama-cli` `b10622` (macOS arm64 릴리스, Metal)                          |
| 모델      | `Qwen3-4B-Instruct-2507-Q4_K_M.gguf` (2.4GB, Apache-2.0, 비사고형 instruct)         |
| 입력      | Phase 1의 실제 71분 발표·Q&A 회의록 — **40,089자 / 약 28,004토큰**(문자당 1.43토큰) |
| 컨텍스트  | `-c 8192`, 청크 예산은 지시문 500토큰을 뺀 나머지 (`src/shared/summary.ts`)         |
| 생성 상한 | `-n 1200`, `--temp 0.3`, 스레드 = 코어 − 2                                          |

## 호출 방식 — 전부 파일로 주고받는다

```
llama-cli -m <모델> -sysf <시스템프롬프트> -f <프롬프트> -o <출력>
          -st --no-escape --no-display-prompt --no-warmup --no-show-timings
          -c 8192 -n 1200 --temp 0.3 -t <스레드>
```

- **`-p`(argv)로 회의록을 넘기지 않는다.** 구간 하나가 9천 자라 argv 길이 제한에 걸린다.
- **`--no-escape` 필수.** `-e`가 기본으로 켜져 있어 본문의 역슬래시 시퀀스를 제어문자로 바꾼다.
- **`-st`(single-turn) 필수.** 없으면 답변 뒤 대화 모드로 들어가 stdin을 기다리며 프로세스가 끝나지 않는다.
- `llama-server`(HTTP)는 쓰지 않는다. 단발 요약에 상주 서버·포트 관리가 필요 없고, 프로세스가 하나 더 늘면
  종료·좀비 처리까지 앱이 떠안는다.

## 구간 분할 (map-reduce)

컨텍스트를 8192토큰으로 둔 이유는 KV 캐시다. Qwen3-4B는 토큰당 약 144KB라 8192토큰이면 1.2GB 수준이고,
이 정도여야 저사양 기기에서도 뜬다. 여기서 생성분(1200)과 지시문 몫(500)을 빼고 문자/토큰 1.4를 곱하면
한 구간의 본문 예산은 **9,088자**가 된다. 실측 비율(1.43)보다 낮게 잡아 예산을 넘기지 않게 했다.

| 구간 | 1     | 2     | 3     | 4     | 5     |
| ---- | ----- | ----- | ----- | ----- | ----- |
| 글자 | 9,033 | 9,018 | 8,966 | 9,078 | 3,989 |

자르는 위치는 **발화 줄 경계**다. 한 발화가 두 구간에 걸치면 화자와 문장이 함께 잘려 부분 요약이 문맥을 잃는다.

## 처리 시간 (map-reduce, 5구간)

| 단계            | 프롬프트 | 출력    | 시간        |
| --------------- | -------- | ------- | ----------- |
| 구간 요약 1     | 9,256자  | 966자   | 47.5초      |
| 구간 요약 2     | 9,241자  | 954자   | 44.9초      |
| 구간 요약 3     | 9,189자  | 1,039자 | 43.2초      |
| 구간 요약 4     | 9,301자  | 836자   | 35.9초      |
| 구간 요약 5     | 4,212자  | 550자   | 17.4초      |
| 합치기 (reduce) | 4,695자  | 960자   | 29.4초      |
| **합계**        |          |         | **218.3초** |

- 71분 회의를 **약 3분 40초**에 요약한다. 회의 길이의 1/20 수준이다.
- 첫 측정은 324초였다. 아래 결함 두 개를 고친 뒤 **240초**로 줄었다 — 최종 요약이 잘리지 않아 reduce가
  반복 생성으로 늘어지지 않았고, 라벨 나열이 사라지면서 출력 토큰이 줄었다.
  위 표는 같은 입력으로 다시 잰 값이고(218.3초), 두 측정의 차이는 다른 작업이 CPU를 함께 쓰던 정도의 편차다.
- 진행률은 map 구간에 80%, reduce에 20%를 배분한다 (`src/main/summary/run.ts`).
- 요약은 STT·화자 분리와 같은 큐(동시성 1)에서 돈다. 회의록 생성 직후 바로 요약하면 대기 시간이 더해진다.

## 확인된 결함과 수정

| 증상                                                      | 원인                                  | 수정                                                                   |
| --------------------------------------------------------- | ------------------------------------- | ---------------------------------------------------------------------- |
| 최종 요약이 문장 중간에서 끊김                            | `-n 900`이 부족                       | `SUMMARY_MAX_PREDICT_TOKENS` 900 → 1200                                |
| "화자 7이 배포를 맡기로 함"처럼 익명 라벨을 담당자로 나열 | 시스템 프롬프트에 금지 지시가 없었음  | "`화자 N` 같은 익명 라벨은 담당자·주체로 쓰지 말라" 지시 추가          |
| `-o` 파일에서 답변만 뽑히지 않음                          | 파일에 `User:` 프롬프트가 함께 들어감 | 프롬프트가 끝나는 지점부터 `\nAssistant:\n` 마커를 찾는다 (`llama.ts`) |
| 회의록에 없는 기한("2025년 4월 10일")을 지어냄            | 근거 없는 값에 대한 금지가 없었음     | 시스템 프롬프트에서 날짜·숫자·이름을 금지하고 없으면 "없음"을 쓰게 함  |

`-o` 파일 형식은 `User:\n<프롬프트>\n\nAssistant:\n<답변>`이다. 파일을 통째로 읽으면 회의록 전문이
요약으로 저장되고, 회의록 본문에 같은 표시가 들어 있을 수 있어 **프롬프트가 끝나는 지점부터** 마커를 찾는다.

## STT 오인식은 요약 단계에서 고치지 않는다 (결정)

요약문에 **"증본 문서"(changeset), "타볼"(tarball), "기터브"(GitHub)** 같은 표기가 그대로 실렸고
모델은 이를 확신에 찬 어조로 되풀이한다. 확인해 보면 **요약 단계의 결함이 아니다** — 회의록 원문에
이미 그렇게 적혀 있고, 요약 모델은 주어진 텍스트를 충실히 옮겼을 뿐이다.

요약 단계에서 고치지 않기로 한다.

- 모델에게 "오인식을 바로잡아라"라고 지시하는 것은 _"회의록에 없는 내용을 만들지 마라"_ 는 시스템 프롬프트와
  정면으로 충돌한다. 추측으로 고치기 시작하면 사람 이름·숫자도 함께 고치려 든다.
- 후처리 치환 사전은 회의마다 용어가 달라 앱에 고정 목록으로 넣을 수 없다.
- Phase 3에서 **발화 인라인 편집**이 들어갔다. 잘못 적힌 용어는 회의록에서 고친 뒤 "다시 요약"을 누르면
  그대로 반영된다. 이 경로가 정확도와 사용자 통제 양쪽에서 가장 낫다.

더 줄이려면 STT 단계에서 다뤄야 한다. whisper.cpp의 `--prompt`(initial prompt)로 도메인 용어를 물려 주는
방법이 있으나, VAD로 잘린 구간마다 효과가 유지되는지 확인되지 않았고 초기 프롬프트 자체가 환각을 부르는
사례가 알려져 있다. **회의별 용어 사전은 Phase 4 이후 과제로 남긴다.**

## 배포 관점 (동봉 자산)

- 릴리스에는 도구가 60개 들어 있지만 `llama-cli`와 그 의존 라이브러리만 꺼낸다 —
  실행 파일 50KB + **dylib 11개, 합계 약 24MiB**.
- **`libllama-server-impl.dylib`(8.9MB)도 빼면 안 된다.** `llama-server`를 쓰지 않는데도 `llama-cli`가
  직접 링크하고 있어 없으면 dyld가 실행을 거부한다.
- `llama-cli`의 `LC_RPATH`는 **`@loader_path`** 다(확인함). dylib을 실행 파일과 같은 폴더에 두면 그대로
  동작하므로 `resources/bin/<platform>-<arch>/` 배치가 맞다.
- 내려받은 상태의 서명은 **adhoc(linker-signed)** 이다. 하드닝 런타임에서 실행하려면 electron-builder가
  Developer ID로 다시 서명해야 하고 `asarUnpack: resources/**`가 그 전제다
  (`references/distribution.md` 6절). 실제 검증은 서명 인증서가 준비된 뒤에 가능하다.

## 남은 문제

- 저사양 장비(메모리 8GB 미만)에서 4B 모델은 스왑을 유발할 가능성이 있다. Qwen3-1.7B 폴백은
  Phase 4 저사양 안내와 함께 검토한다.
- Windows 실기 검증. 필요한 파일 집합은 확정했으나(`references/distribution.md` 10.2절)
  실제 Windows에서 `llama-cli.exe`가 뜨는지는 확인하지 못했다.

## 결론 (SKILL.md 결정 표에 반영됨)

- `llama-cli` 파일 입출력(`-sysf`/`-f`/`-o`) + `-st --no-escape --no-display-prompt --no-warmup` 조합으로 고정.
- 청크 예산은 컨텍스트 8192의 약 80%를 넘기지 않는다. 71분 회의는 5구간으로 나뉘며 품질은 한 번에 요약한
  10분 발췌와 같은 수준이었다.
- 요약 모델은 필수 모델이 아니다. 온보딩에서 받지 않고 설정에서 따로 받는다.
- 요약은 자동 실행이 아니라 사용자가 버튼으로 요청한다 (3~4분이 걸리고 모델도 선택 사항이다).
- 요약 실패는 회의 상태(`meetings.status`)를 건드리지 않는다. STT 결과는 그대로 남는다.
